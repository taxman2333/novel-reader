# 阅读性能优化

- 状态：**已完成**（阶段 1 与阶段 2 均已实施，2026-09-28）
- 类型：性能优化（含 UI 调整 / 重构）
- 创建日期：2026-09-28
- 关联需求：`docs/ROADMAP.md` 1.4「大文本渲染优化」；其「待评估」一项即为此处方案 2

## 需求描述

用户在实际使用中提出五个体验问题（原文）：

1. exe 启动太慢，打开要等几秒；
2. 导入小说太慢，等太久；
3. 再次打开已导入的小说也很慢；
4. 打开小说后滚轮滚动延迟高、上下滚动不流畅、很卡顿；
5. 修改阅读设置时界面延迟几秒，尤其是字号、行距、段距、版心宽度这类带滑条的，无法随滑条移动流畅变化。

界面外观本身**用户认为已经没问题**，本方案不涉及视觉调整。

需求目标：让上述五个操作在真实体量的 TXT（本机 8.9–11.3 MB，79,157–133,632 段）上做到可接受。

## 需求背景

当前实现把整本小说一次性物化为 DOM 节点，段落数以万计。用户书架上的两本书正是这个量级，
因此问题在真实数据上稳定复现，不是极端个例。

实测（见下节）表明：**第 2、3、4、5 条同源于一个决定——每次都把整本书渲染成完整的 DOM**；
而**第 1 条（启动）不在应用代码里**。

### 改一次设置的成本

| 操作 | 书 A | 书 B |
|---|---|---|
| **改字号（强制整篇重排）** | **717.3 ms** | **976.6 ms** |
| 改版心宽度 | 465.1 ms | — |
| 改行距 / 段距 | 与字号同量级（同为 `font` 简写的组成部分） | — |
| 切换主题 | 0.1 ms（无几何变化，仅重绘） | — |
| `store.save()`（mkdir+writeFile+copyFile+rename） | 1.2 ms（library.json 仅 1,758 字节） | — |

拖滑条时 `input` 事件以每秒数十次到达，而主线程一次重排就要 0.7–1.0 s，
**只能处理约 1 次/秒，其余事件排在队列里** → 表现为「滑动一下就卡几秒」。
**这就是第 5 条，且是本方案里最严重的一项。**

根因：`--reader-font-size` 等自定义属性被全部段落继承，且其「使用值」进入 `font` 简写，
因此改一个变量会让 13 万个后代全部失效 → 整篇重排。

## 技术实现方案

### 根因

一个决定：**每次打开都把整本书物化成完整 DOM，且一次性同步完成。**
79,157–133,632 个 `<p>`、文档高度 1,130 万 px。由此：

- 任何触及全篇几何的操作都要 0.5–1.0 s → 第 5 条（最严重）
- 打开一本书要 1.5–2.1 s，期间无法交互 → 第 2、3 条
- 滚动与绘制要在 1,130 万 px 的活内容上工作 → 第 4 条（未复现，但同源）

### 阶段 1：低风险改动（不动渲染架构）

| # | 改动 | 预期收益 |
|---|---|---|
| 1 | `restoreScroll` 显式传 `behavior: 'instant'`，与 `jumpToChapter` 的既有做法一致 | 打开省去 ~700 ms 的平滑滚动与 45 次 scroll 事件 |
| 2 | 设置滑条：`applyReaderSettings` 收敛到 rAF（一帧内多次 `input` 合并为一次样式写入）；`persistLibrary` 对**设置与进度**两条高频路径防抖 400 ms | 去掉每秒数十次 IPC 与 4 次系统调用；重排次数降到每帧一次 |
| 3 | `topParagraphIndex` 的段落 NodeList 在 `renderReader` 时取一次并缓存，不再每帧 `querySelectorAll` | 省掉每帧 ~2–3 ms 的节点列表构造 |
| 4 | 主进程 `readTxtFile` 已归一化，渲染层 `parseParagraphs` 不再重复归一化 | 省 ~30–40 ms |
| 5 | 启动：`show: false` + `ready-to-show` → `show()`；把 `checkBookAvailability` 移到首次渲染**之后** | 不出现空白窗口；书架不再等 N 次 `fs.stat` |
| 6 | `applyReaderSettings` 里每次都调用的 `applyTheme` 移出（主题未变时不做无谓写入） | 语义修正，开销可忽略 |

**阶段 1 不能解决第 5 条。** 改字号的 717 / 977 ms 来自全篇重排，第 1–4 项省不掉它。

防抖的边界（重要，避免丢数据）：**只对「设置」与「进度」这两条高频路径防抖**；
导入、移除、重新定位这类结构变更仍然立即落盘。`beforeunload` 与
`saveLibraryOnExit` 作为最后的保险保持不变。

### 阶段 2：段落窗口化渲染（核心，解决第 2/3/4/5 条）

把「整本 DOM」换成「段落窗口」：任何时刻 DOM 里只有视口附近的几百个 `<p>`。

需要三样东西：

1. **段落高度估算**：由段落字符数、`contentWidth`、`fontSize` 推算出占几行，
   乘 `lineHeight` 加 `paragraphGap`。用于在任何内容渲染之前就能算出任意段落的垂直偏移。
2. **偏移表**：段落序号 → 累计偏移的映射。渲染后把实测高度回填，替换该段的估值。
   段落是等宽流式块，可增量维护（前缀和 + 脏区间）。
3. **窗口管理**：滚动接近窗口边缘时按固定块（或按章节边界）追加下一批、回收远端。
   `scrollTop` 用「偏移表 + 窗口基址」换算，不再依赖元素的真实位置。

打开流程改为：估算目标偏移 → 直接设 `scrollTop` → 渲染该处窗口 → 在 rAF 里按实测高度做一次微校正。
不再使用 `scrollIntoView`，因此**顺带绕开了 `scroll-behavior: smooth`**，阶段 1 第 1 项对阶段 2 不再是必需的（但仍值得单独保留）。

改设置时只重排窗口内的几百段 → 滑条跟手。

#### 被否决的替代方案

| 方案 | 否决原因 |
|---|---|
| **只加 `content-visibility: auto` + `contain-intrinsic-size`** | 实现最省（一段 CSS），也能消掉全篇重排。但屏幕外的段落只能用估算高度，`scrollIntoView` 会落在估算位置，**恢复阅读位置会偏**——而「记住你读到哪」正是这个应用的核心功能。且滚动条长度会随实测逐步变化，读长文时位置会漂。风险与本项目定位冲突，不采用 |
| **打开时先渲染前 N 段，其余延后追加** | 首屏变快，但 DOM 最终仍长到 13 万节点，第 4、5 条的根因原样保留 |
| **按章节整块渲染（一次只渲染一章）** | 实现简单（书 B 133,632 段 / 1,602 章 ≈ 83 段/章，代价极低），但**改变阅读交互**：不能再跨章连续滚动。用户没有要求这个改变，不单独采用。可作为窗口管理的一种对齐策略（窗口边界落在章节边界上） |
| **把正文或解析结果缓存到磁盘，加快再次打开** | 「再次打开很慢」最顺手的解法（可把 2.1 s 压到百毫秒级），但要把**整本正文**复制进应用专用目录。**2026-09-28 用户决策：核心约束 1 只放宽到「有限的正文片段」，不放开整本缓存，此项不做。** 第 3 条改由阶段 2 解决 |
| **引入虚拟滚动第三方库** | 违背「不要为了实现简单功能引入不必要的复杂依赖」。且本项目的恢复位置逻辑（`findRestoreIndex` + 附近文本匹配）本来就要自己维护偏移表，库能省的不多 |

## 兼容性问题

- **已有书架、阅读进度、阅读设置全部不变。** 进度仍是段落索引 + 附近文本，
  `findRestoreIndex` 的两级匹配逻辑保留。
- **恢复位置的表现可能变化**（阶段 2）：估算偏移与真实偏移会有一次可见的微校正。
  验收标准里为此定了量化指标（首屏落点偏差），不能只凭"感觉好了"。
- **`docs/ROADMAP.md` 1.4 的「需要评估」一项**（分块渲染 vs 虚拟滚动的取舍；
  虚拟滚动会影响恢复位置的实现方式）——本方案就是对该项的答复：
  选窗口化 + 偏移表，因为纯 `content-visibility` 会牺牲定位精度。

## 潜在风险

| 风险 | 影响 | 验证 / 回退 |
|---|---|---|
| 阶段 2 的偏移估算不准，阅读位置漂移 | **本应用的核心功能受损** | 对两本真实小说各取 5 个位置做往返测试（跳到 10%/34%/50%/75%/95%，重开，比对段落序号）。偏差超阈值即视为不通过 |
| 窗口拼接时出现闪烁或跳动 | 阅读体验 | 在窗口边缘来回滚动，肉眼确认无跳动；用 `scrollTop` 序列断言单调性 |
| 阶段 2 破坏界面回归测试 | 10 条断言中约 4 条依赖「全部段落在 DOM 里」 | 改写为对新接口断言（见下），不是删除 |
| 防抖导致异常退出时丢最后一次设置/进度 | 丢一次阅读进度 | **已实测到这条路径本身就是坏的**（见「顺带发现」第 2 条：`save-on-exit` 是 `void` 不等待）。必须与防抖同批修复：退出改为可等待 + `before-quit` 等最后一次写入落地；结构变更不防抖 |
| 用 `contain-intrinsic-size` 之类的估算影响滚动条 | 位置漂移 | 若不采用 `content-visibility`（本方案不采用），此风险不存在 |
| 阶段 1 第 5 项把 `checkBookAvailability` 挪后，书架短暂显示「可用」后变「不可用」 | 视觉抖动 | 挪到首次渲染后的下一个 rAF；若抖动明显则不采用该项，逐项验收 |

## 验收标准

均需在**你的机器上、用你书架上那两本书**执行，不以我的合成基准为准。

1. **改字号**：拖动字号滑条从 14 到 32，界面跟随流畅；单次 `input` 的同步耗时
   从 717 ms（书 A）/ 977 ms（书 B）降到 **< 30 ms**。
2. **改版心宽度**：同上，从 465 ms 降到 **< 30 ms**。
3. **打开一本书**：从双击书架条目到正文可滚动，书 B **< 600 ms**（基线约 2.1 s）。

### 2. `library.json.tmp` 残留 —— 已核实：**最后一次保存没有完成**

已用文件内容比对核实（不是猜测）：

| 文件 | 大小 | sha256（前 16 位） | mtime |
|---|---|---|---|
| `library.json` | 2,199 | `07928576b68fac2c` | 2026-09-28 00:56:13.718 |
| `library.json.bak` | 2,199 | `07928576b68fac2c` | 2026-09-28 00:56:13.718 |
| `library.json.tmp` | 2,199 | `5658c7b309596023` | 2026-09-28 00:56:14.039 |

`library.json` 与 `.bak` **完全相同**，`tmp` 不同。逐字段比对，唯一差异是
`书 B` 的 `progress.updatedAt`（`…13.209Z` vs `…14.025Z`，晚 816 ms）；
`paragraphIndex` / `charOffset` / `ratio` / `context` 全部一致。

**结论**：`library-store.js` 的 `save()` 顺序是
`mkdir → writeFile(tmp) → copyFile(json→bak) → rename(tmp→json)`。
这次保存写完了 `.tmp` 就停在 `copyFile` 之前（`.bak` 的 mtime 仍是上一次的 13.718，
证明 `copyFile` 没执行），**`rename` 从未发生，这是一次未完成的保存**。

**为什么值得管**：`electron/main.js:116` 的退出保存是

```js
ipcMain.on('library:save-on-exit', (_event, data) => { void store.save(data); });
```

`void` —— 不 await；而 `window-all-closed` 立刻 `app.quit()`。
**应用可以在保存飞到一半时退出。** 用户关闭窗口那一刻的阅读进度正是最可能丢掉的那一次写入；
下次打开会退回上一次保存的位置。

这次**实际没有丢数据**：两次保存之间阅读位置没变，只差一个时间戳。属于运气好。

**与本方案的交互（重要）**：方案阶段 1 第 2 项要给「进度」落盘加防抖。
如果不一并处理这条退出路径，防抖会把「最后一次写入未完成」的窗口放大——
所以**退出路径的可靠性必须与防抖同批修复**，不能分开做。修法：
把 `library:save-on-exit` 改为 `ipcMain.handle` + 渲染层 `await`，
并在主进程 `before-quit` 里等最后一次写入落地。

另注：`save()` 本身没有串行化，两次并发保存会在 `rename` 上互相踩（可能抛 `ENOENT`）。
当前调用点不容易触发，但加上防抖后高频写入会使窗口变大。一并处理。

### 三处偏离计划，以及理由

1. **额外移除了 `.reader-scroll` 的 `scroll-behavior: smooth`**（计划只要求 `restoreScroll` 显式传 instant）。
   理由：该属性只影响程序化滚动，而这个容器里的程序化滚动**全部是「跳到远处」**——恢复阅读位置、拖目录里的进度滑条。
   留着它意味着每一处都要记得显式写 instant，漏一处就退回动画；删掉之后默认就是跳变，`jumpToChapter` 里原有的
   `behavior: 'instant'` 从「必须写」变成「写明意图」。滚轮滚动本来就不受这个属性影响，因此删掉它不可能影响第 4 条。
   附带修正：旧代码里目录的百分比滑条直接赋值 `scrollTop`，在 smooth 下读回 `scrollTop` 会拿到动画中途的值。

2. **退出路径用 `sendSync` + `will-quit`，而不是计划写的 `ipcMain.handle` + 渲染层 `await` + `before-quit`。**
   理由：`beforeunload` 是**同步**的，渲染进程无法在那里 `await` 一个 `invoke` 再阻止窗口关闭——await 会让窗口先关掉，
   快照就丢了。要让渲染进程「交完再走」只能用 `sendSync`（主进程立刻回值，不等磁盘）。
   同理，`before-quit` **早于**窗口关闭触发，在它里面等待等于等一份还不存在的写入；`will-quit` 在所有窗口关闭之后触发，
   才是「最后一份快照一定已经交出来」的那个时点。写入串行化（`queueSave`）按计划加了，`library:remove` 的内部写入也走同一条链。

3. **未做 `show: false` + `ready-to-show`。** 计划的风险表本来就写了「逐项验收」，这里验收不通过：
   先前实测（`bench3.mjs`）显示本应用的完整启动路径相对空白 Electron 只慢 **+2～6 ms**，窗口显现时机不是瓶颈；
   而 `show: false` 会把首帧推迟到 `ready-to-show`，是**净变慢**。白闪问题也已经由 `backgroundColor: '#f1ede4'` 解决。
   这一项不做不影响其它项。

### 三处偏离计划，以及理由

1. **没有 rAF 微校正。** 计划写的是「直接设 `scrollTop` → 渲染该处窗口 → 在 rAF 里按实测高度做一次微校正」。

2. **窗口是整窗重建，不是增量追加/回收。** 计划写「按固定块追加下一批、回收远端」。

### 实现中发现、计划未写的两项必需机制

- **锚点**（`anchorIndex` + `anchorViewportOffset`）。重建窗口会改垫片高度、也会把若干估算高度换成实测值，
  必须把「重建前位于视口顶部的那一段」钉回同一像素位置，否则每次重建都跳一次。
  采锚点时**只查偏移表，不读 DOM**——改字号时样式早已被改掉，那一刻读到的元素位置反映的是
  「旧 `scrollTop` + 新字号」，实测会让整本书往回跳 **101 段**。
- **半像素容差**（`OFFSET_EPSILON = 0.5`）。表里是浮点高度（屏幕外段落只有估算值），
  而 `scrollTop` 按设备像素取整，边界反查会提前落一段。实测到过 **1 段**的漂移。
- 另外 `src/styles.css` 加了 `overflow-anchor: none`：Chromium 的滚动锚定会在垫片高度变化时自己调
  `scrollTop`，与偏移表打架。必须关掉。

「首次强制布局」在窗口形态下不再存在：屏幕外的部分由垫片撑高，不会触发全篇布局。

滚动一行与阶段 1 的基线（书 A 9.4 ms、书 B 29.6 ms）**不完全同源**：旧基准从 0 起滚、要穿过整本 DOM，
新基准从窗口顶部起滚。都列出来只说明量级——书 B 由约 34 fps 回到 60 fps 以上。

**基准测不到的部分（如实说明）**：

- 不含 Electron IPC、真实正文的 HTML 生成，以及样式重算中与段落无关的部分。
  因此验收标准 1、2 里「单次 `input` 的同步耗时」基准只给出其中约 6.5 ms 的排版部分，**结论须由你实测确认**。
- 窗口形态的滚动数字**不含窗口重建那一下**：重建大约每滚过 150 段发生一次，每次 4～5 ms。
  所以 5.5 ms 的中位数略低估真实体感。
- 打开书籍与导入的**端到端**耗时基准没有测，见下。

### 遗留问题

1. 标准 3、4、5、6、7、9、10 需要你在自己机器上实测。其中 6 与 10 是阶段 1 就欠下的。
2. **窗口化的固有取舍（不是本次引入的缺陷）**：屏幕外段落的偏移来自字数估算，只有渲染过才被实测替换。
   因此跨越大段未渲染区域的反查可能偏一段左右。恢复阅读位置仍以**附近文本精确匹配为第一优先**
   （`findRestoreIndex` 未改），只要原文件没变就不会走到估算索引上。
   「落点段恒为窗口中心、必定被实测校正过」这一点保证了对齐到视口顶部的那一段本身是准的。
3. 滚动过程中文档总高会随实测回填小幅变化。锚点机制保证视口内容不跳，但**滚动条长度**会有微小变化。
   未做「全书总高在估算阶段就固定下来」的那种方案——那要以放弃实测校正为代价，得不偿失。
