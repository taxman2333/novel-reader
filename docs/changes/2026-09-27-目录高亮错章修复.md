- 创建日期：2026-09-27

> 用户直接报障并要求修复，因此未走 `/change` 出方案再实现的流程，而是按「先复现、再定位、后修复」的顺序直接处理，并把诊断与验证过程记录在此。

## 需求描述

**用户原始表述**：

> 在我使用目录点击某一章节后，跳转的章节位置没问题，但是我再次点开目录时，发现目录上某一章节有个高亮显示，按理来说这个高亮显示应该是高亮我刚刚选择的那个章节，但是实际并不是，比如我选择跳转到60章，但是再次打开目录，发现52章的目录高亮了，另一本小说选择跳转到60章，打开目录又发现是66章的目录高亮了

**精确表述**：跳转本身正确（正文确实停在目标章开头），但目录里标记为"当前章节"的那一项是错的，偏差随书不同、方向也不同。

## 根本原因

`src/main.js` 的 `refreshActiveChapter()` 用**滚动比例估算**出的段落索引来判断当前章节：

```js
const next = currentChapterIndex(getProgressFromScroll(scroll, paragraphs).paragraphIndex);
```

而 `src/reader.js` 的 `getProgressFromScroll()` 是这样算段落索引的：

```js
const ratio = scrollTop / (scrollHeight - clientHeight);
const paragraphIndex = Math.floor(ratio * (paragraphs.length - 1));
```

这是**线性插值**，隐含假设「所有段落高度相同」。真实小说的段落长度差异极大——对话密集的段落可能只有几个字，长描写段落可能有几百上千字，一屏之内的高度可以相差数倍。段落高度不均时，像素比例与段落序号之间不再是线性关系，误差随阅读深入不断累积：

- 若前面的段落平均更高，估算值会**偏小**（跳到第 60 章 → 高亮第 52 章）；
- 若前面的段落平均更矮，估算值会**偏大**（跳到第 60 章 → 高亮第 66 章）。

用户报的两个例子方向相反，正是这个偏差方向的体现——它取决于每本书自身的段落长度分布。跳转本身用的是 `scrollIntoView`，精确无误，所以"位置对了、高亮错了"。

**这不是新引入的缺陷**。`docs/changes/2026-09-27-章节目录.md` 的技术方案第 4 节明确写了「代价是章节高亮基于『比例 × 段落数』的估算，段落长度差异大时可能偏一章……此项列为已知限制」。当时的判断是「偏一章、且与应用现有的进度模型同一套口径，可以接受」。实测证明这个判断偏乐观：偏差不是一章，而是十几章，且方向不定。

## 复现与量化

缺陷在现有测试夹具下**完全不可见**：`tests/ui/entry.mjs` 的段落文本长度几乎相同，此时「比例 × 段落数」恰好准确，所以 9 项用例全绿。

因此先写了一个临时诊断脚本，用**段落长度随编号线性增长**的合成书（模拟长短段分布不均），跳到不同章节后对比「视口顶部段落的真实索引」与「比例估算索引」：

| 跳转到 | 顶部真实段落（真实所属章） | 比例估算段落 | 目录实际高亮 |
|---|---|---|---|
| 第 2 章 | 42（第 2 章） | 15 | **第 0 章** |
| 第 5 章 | 105（第 5 章） | 63 | **第 3 章** |
| 第 8 章 | 168（第 8 章） | 142 | **第 6 章** |

估算值系统性偏低，偏差随深入而增大——与用户报的现象同源同形。诊断脚本用完即删。

## 技术实现方案

核心：**改为测量视口顶部段落的真实索引**，并解决"几何测量会强制同步布局"这个当初促成估算方案的问题。

### 1. 二分查找而不是逐段扫描

段落是正常流的块级元素，`bottom` 沿文档顺序单调递增，因此可以二分：

```js
function topParagraphIndex(scroll) {
  const items = scroll.querySelectorAll('#reader-content p');
  if (!items.length) return -1;
  const top = scroll.getBoundingClientRect().top + 2;
  let low = 0;
  let high = items.length - 1;
  let found = -1;
  while (low <= high) {
    const mid = (low + high) >> 1;
    if (items[mid].getBoundingClientRect().bottom > top) {
      found = mid;
      high = mid - 1;
    } else {
      low = mid + 1;
    }
  }
  return found < 0 ? -1 : Number(items[found].dataset.paragraphIndex);
}
```

数千段也只需约 12 次 `getBoundingClientRect`，且首次读取已经强制布局，后续读取命中已算好的几何，不再触发布局。**被否决的替代方案**：逐个 `findIndex`（线性扫描，数千段最多数千次读取）；缓存段落偏移表 + 失效机制（要在字号/行距/段距/版心/字体/主题/窗口尺寸七处正确失效，任何一处漏掉都会静默错位）。

### 2. 用 rAF 把滚动期间的重算收敛到每帧一次

滚动事件一帧内可以触发多次，测量几何又必须避免同帧反复触发布局。因此不动滚动事件里已有的进度保存链路，只把章节重算挪进 `requestAnimationFrame`：

```js
function scheduleActiveChapterRefresh() {
  if (chapterRefreshFrame) return;
  chapterRefreshFrame = requestAnimationFrame(() => {
    chapterRefreshFrame = 0;
    refreshActiveChapter();
  });
}
```

`{ passive: true }` 的滚动监听仍照常计算并防抖保存进度，只有章节高亮这一步被推迟到帧边界。用户的观感是「高亮跟着滚动走」，每帧更新一次已超出可感知上限。

### 3. 没有改动的部分

- **`getProgressFromScroll()` 一行未改**。它同时服务于「保存阅读进度」，而改变保存出去的值会改变 `library.json` 里 `paragraphIndex` 的含义，属于需要单独评估的数据语义变更（该偏差已记入 `docs/PROJECT.md` 第 9 节第 7 条）。
- 章节识别、面板开关、跳转本身、样式全部未动。

## 潜在风险

| 风险 | 应对 |
|---|---|
| 二分查找假设段落 `bottom` 单调递增 | 段落是 `.reader-content` 内正常流的块级元素（`src/styles.css:80`，仅 `margin`/`padding`/`text-indent`，无浮动或绝对定位），单调性成立。若将来出现多列或绝对定位排版，必须重新评估 |

### 与原方案的偏差

**推翻了 `2026-09-27-章节目录.md` 中的一项设计取舍。** 该方案为避免在滚动事件里做几何测量，刻意改用比例估算，并把它列为「已知限制」。本次修复证明：

- 该限制的实际量级远大于方案估计的「可能偏一章」——实测偏差可达 2 章以上，用户实测达 6~8 章；
- 避免几何测量的目标仍可达成，方式是**二分查找 + rAF 收敛**，而不是放弃准确性。

原方案文件保留不改（它是当时的决策记录），仅在末尾加一行指向本次修复。

### 未验证的部分

- **未做交互式 `npm run dev` 目视确认**。当前环境无可交互显示，用户在真实小说上的观感（长按滚动时高亮是否跟手、快速拖动滚动条时是否有可察觉的滞后）无法由我验证。自动化断言覆盖的是「高亮等于顶部段落所属章节」这一正确性，不覆盖流畅度。
- **滚动性能未做基准测量**。论证是「每帧最多一次测量、单次约 12 次 rect 读取」，但没有实测帧率。若在超大长篇上观察到卡顿，可退回「缓存偏移表 + 失效」方案，但那需要处理七处失效点。

### 一并发现、未修复的独立问题

1. **保存的阅读进度 `paragraphIndex` 仍是估算值**，与本次修复同源。影响有限（恢复时首先按上下文精确匹配），但上下文匹配失效时会退到这条有偏差的索引上。修它会改变 `library.json` 中进度字段的含义，属独立变更。已记入 `docs/PROJECT.md` 第 9 节第 7 条。
2. **`renderReader()` 重建 DOM 后 `activeChapterItem` 指向旧节点**：若章节序号未变，新的列表项不会补上 `.is-active`，表现为「重渲染后高亮消失」。本次未改判定条件，因此该问题仍然存在。触发路径有限（重渲染发生在恢复默认设置、重新打开书籍等时刻），需要时可另开变更。
