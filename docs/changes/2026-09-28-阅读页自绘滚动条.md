# 阅读页滚动条改为自绘

- 状态：**已完成**（2026-09-28）
- 类型：Bug 修复 + UI 调整
- 创建日期：2026-09-28
- 关联需求：无（用户实测反馈，在「阅读性能优化」验收期间提出）

## 需求描述

用户原始反馈：

> 我拖动界面右侧的滚动条的时候，滚动条会直接自己滑到最下方，无论怎么往上拖都不动了，请修改。

澄清后的准确表述：**阅读页右侧的原生滚动条在长书上是不可用的**——按下并拖动时内容会一路跑到全书末尾，
之后再拖也回不到想要的位置。用户确认要「自绘一条滚动条」（滑块永远抓得住、拖动按全书比例定位、
点空白轨道翻一屏，滚轮与键盘保持原生手感）。

## 需求背景

阅读一本几百章的小说时，滚动条是唯一的「远距离定位」手段（滚轮只能一屏一屏走）。它失效意味着
用户要么一路滚到底，要么绕过目录面板去用进度滑条——而右侧那条滚动条看起来是能用的，这比没有更糟。

## 当前项目状态

- 正文区是 `.reader-scroll`（`overflow: auto`），文档高度 = 整本书的高度。第 4.4.1 节的窗口化渲染只减少
  DOM 节点数，**不改变文档高度**：屏幕外的部分由 `.reader-spacer` 按偏移表撑出来，仍是一比一。
- 原生滚动条由 Chromium 按 `视口高 / 文档高` 决定滑块长度。

## 变更原因

实测（`tools/_probe-thumb.mjs`，一本 7 万段的合成书，视口 764px）：

- 文档高 **6,098,611px** → 滑块按比例只有 **0.10px**；Chromium 按最小长度兜底，画出来是贴在轨道最顶端
  约 10px 的一小截（截图确认），下面 750 多 px 全是空白轨道。
- 于是**拖动 1px ≈ 8000px 正文 ≈ 10 屏**，轻微一动滑块就按比例飞到最下方。
- 而按在空白轨道上（滑块只有 10px，绝大多数点击都会落空）Chromium 会**朝按下的方向持续翻页、按住不停**，
  表现出来正是「自己滑到最下方、再往上拖也不动」。用户描述的每一句都对得上这两条。

**这不是窗口化引入的**：优化前整本物化成 DOM 时文档高 1130 万 px（比现在还长），滑块只会更抓不住。
用户此前没有拖过这条滚动条，因此直到现在才发现。

三个探针（`_probe-scrollbar`、`_probe-drag`、`_probe-drag2`）先后排除了「窗口重建时 `paint()` 写
`scrollTop` 与拖动打架」这条假设：一次性跳变、逐帧模拟拖动、估算误差（纯汉字 Δ≈0）都表现正常。
合成的鼠标事件也驱动不了原生滚动条，所以这条问题只能在真实鼠标下复现——**结论只能靠量文档高度得出**。

## 技术实现方案

自绘一条覆盖在正文右侧的滚动条：

1. **隐藏原生滚动条**：`.reader-scroll` 上加 `scrollbar-width: none` 与 `::-webkit-scrollbar { width: 0 }`。
2. **结构**：正文区外面套一层定位容器 `.reader-viewport`，自绘轨道绝对定位在其中，高度与滚动区严格一致
   （工具栏高度、「文件有变化」提示都不必写进 CSS）。
3. **滑块长度** = `max(24px, 轨道高 × 视口高 / 文档高)`；长度为轨道全高（无可滚动内容）时整条隐藏。
4. **拖动** = 按全书比例定位：`scrollTop = ratio × max`。文档与正文一比一，因此 `scrollTop / max` 就是全书进度，
   与目录面板的进度滑条同一套换算。写完立刻 `syncViewport()` 重建窗口（滚动事件要等下一个任务才到，
   否则中间那一帧会露出还没换上内容的空白区）。
5. **点空白轨道** = 翻一屏：`scrollTop ± clientHeight`（一比一，正好一个视口高度）。
6. **滚轮落在轨道上转发给正文**，否则右侧会有一条 15px 的死区。
7. 位置与长度每次从 `scrollTop/scrollHeight` 现算并做写入缓存，滚动事件里只写变化过的值。

### 被否决的替代方案

- **把文档高度压短**（让滑块比例变大）：压到滑块有 20px 需要压缩 209 倍，而压缩后 `scrollTop` 的 1px 要分摊
  200 多 px 正文——滚轮一格得动不到 0.5px 才等价于现在的滚动感，点一下空白轨道要跳 200 屏。原生滚动条的
  其它交互（轨道翻页、PgUp/PgDn、Home/End）都按文档高度换算，与「滑块要够长」直接冲突。**原生滚动条在这个
  文档高度上没有可用解**，只能接管。
- **只隐藏原生滚动条、不做替代**：右侧连位置指示都没有了，且用户明确选了自绘这条。

## 潜在风险

| 风险 | 处理 |
|---|---|
| 隐藏原生滚动条后正文宽度变化，影响段落高度估算 | `.reader-content` 的宽度取自 `min(var(--content-width), 100% - 56px)`，宽窗口下与滚动条无关；界面测试 `windowing` 的垫片断言未变（331,817px），确认无漂移 |
| 用过滚动条后键盘翻页失效（`.reader-scroll` 失去焦点） | 指针按下时把焦点交给滚动区 |
| 程序化聚焦在 Chromium 里被当作键盘焦点，默认轮廓框住整块正文 | 指针路径挂 `.is-pointer-focus` 压掉轮廓，一按键盘就摘掉；键盘焦点仍保留可见轮廓。实测：指针之后 `outline: none`，按过键盘后恢复 3px 绿色轮廓 |
| 拖动时指针移出窗口导致拖动状态卡住 | `pointerup` / `pointercancel` / `blur` 三处都结束拖动 |

## 验收标准

1. 长书（几百万 px）上，滑块长度 ≥ 24px，始终抓得住 ✓（`scrollbar` 用例断言）
2. 拖动滑块到轨道某个位置，正文落到全书对应比例，且滑块画在同一位置 ✓（拖到中间 → 4200 段的第 2096 段 / 50.0%）
3. **拖一小段只走一小段**，不再「一拖就到底」 ✓（再拖 10% → 60.0%）
4. 点空白轨道 = 翻一屏 ✓（764px = 一个视口高度）
5. 滚轮、PageUp/Down、空格仍能正常滚动 ✓（滚轮在轨道上的转发有用例；键盘路径无自动化断言，须手测）
6. 整本装得下一屏时不出现滚动条 ✓（`scrollbar-short-book` 用例）
7. 四套主题下滚动条都要看得见、不刺眼 ✗ **未逐一套截图确认**（用的是主题变量 `--reader-muted`，随主题变化）
8. 拖动滚动条后，键盘翻页仍然有效 ✓（实现上显式交还焦点；**须手测确认**）

## 实施记录（2026-09-28）

**逐项对照验收标准**：1～4、6 由 `scrollbar` / `scrollbar-short-book` 两个用例自动断言通过（实测输出：滑块
24px / 轨道 764px，点轨道翻屏 764px，拖到中间落到第 2096 段（50.0%），再拖 10% 到 60.0%）；5 的滚轮部分有
断言，键盘部分与 8 须你在真实应用里手测；**7 未做**（我只在默认「暖色」主题下截图确认过，四套主题没有逐一套
截图）。

**实现中发现、计划里没写的两处**：

1. 拖动结束后正文区外面多出一圈默认焦点轮廓。原因是 `focus()` 这类程序化聚焦在 Chromium 里同样会被算作
   键盘焦点——实测即使刚发生过可信的鼠标点击，`focus()` 之后 `:focus-visible` 依旧成立，所以只靠
   `:focus-visible` 挡不住。改为显式区分：指针路径挂 `.is-pointer-focus` 压掉轮廓，一按键盘就摘掉。
2. 滚轮落在轨道上会变成死区（轨道压在正文右侧一条上，且与 `.reader-scroll` 是兄弟节点）。补上转发。

**实测数据**（`tools/_probe-thumb.mjs`，7 万段合成书、视口 764px）：文档高 6,098,611px、原生滚动条占宽 0px、
轨道 764px、滑块 24px；拖到轨道 40% → `scrollTop` = 2,439,130（40.0%），正文换到第 27998 段。
截图存档：`scrollbar-top-window.png`（顶部）、`scrollbar-mid-window.png`（40% 处）。

**测试**：

- `npm test` → 35 项通过（未改动单元测试）。
- `npm run test:ui` → **13 项通过**（新增 2 项）。`windowing` 的垫片断言 331,817px 未变，说明隐藏原生滚动条
  没有影响段落高度估算。
- `npm run build` → 通过（`dist/` 产物正常）。

**遗留问题**：

1. 验收标准 7（四套主题下的观感）与 5/8 的键盘路径须你手测。
2. 拖动滑块是**粗调**：6 百万 px 的书上 1px 轨道 ≈ 10 屏，落点无法精细到某一段；精细定位仍靠滚轮与目录。
   这是把全书映射到 700 多 px 轨道的固有分辨率，不是缺陷。
3. `tools/_probe-*.mjs` 四个一次性排查脚本用完即删，本次已删除，不入库。
