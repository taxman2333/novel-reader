## 需求描述

**用户原始表述**：

> 目前这个版本已经满足了基本需求，我想在 github 发布一个 release，我想知道我这个项目应该如何打包，是直接打包为压缩包，还是打包为应用，给我你的建议

**澄清后的准确表述**：

1. 为项目配置 Electron 打包，产出一个**可以在没有 Node.js 环境的电脑上直接运行**的 Windows 应用；
2. 以 GitHub Release 的形式发布该产物，并打上 `v1.0.0` tag；
3. 打包与发布**不改变应用现有行为**，尤其不得让已有用户的 `library.json` 失效。

**先澄清一处措辞**：「压缩包」在本需求里指两种不同的东西，二者不是二选一的关系：

| | 内容 | 拿到的人需要做什么 | 谁来生成 |
|---|---|---|---|
| **源码压缩包** | `src/`、`electron/`、`package.json` 等 | 装 Node.js → `npm install` → 命令行启动 | GitHub 每次 Release **自动生成两份**（Source code zip / tar.gz），不需要手工制作 |
| **应用压缩包** | exe + Electron 运行时 | 解压 → 双击 | 需要 electron-builder 打包 |

**本次要新增的是后者。** 只发源码压缩包不成立：项目定位是桌面应用，让拿到的人先装一整套 Node 环境才能看小说不合理。

## 需求背景

## 技术实现方案

### 1. 打包目标：`zip`（免安装目录版），不做安装程序

electron-builder 的 Windows 目标里，本需求选 `zip`：

```
release/novel-reader-1.0.0-win-x64.zip
└── 解压后：书页之间.exe + 运行时文件（dll / pak / locales …）
```

**理由**：

1. 解压双击即用，零依赖，这是本需求的核心目的。
2. **不写注册表、不装进 `Program Files`**，卸载等于删文件夹——与项目「本地、无侵入」的定位一致。
3. **启动速度与开发时一致**。对比之下 `portable`（单文件 exe）每次运行都要把约 200MB 解压到 `%TEMP%` 再启动，明显更慢，且更易被杀毒软件误报。

**被否决的替代方案**：

| 方案 | 否决理由 |
|---|---|
| **NSIS 安装程序** | 写注册表、装进 `Program Files`、带卸载项。对一个自用工具过重，且引入额外的卸载残留问题 |
| **`portable` 单文件 exe** | 只胜在「一个文件好转发」。本需求的受众是用户自己，不需要转发；换来的是每次启动的解压开销。**若将来确实需要转发单文件，它是加一个 target 的事，不影响本次决策** |
| **只发源码压缩包** | 见「需求描述」——拿到的人需要完整 Node 环境 |
| **`dir` 目标（不压缩）** | 也要产出，但作为中间产物用于验证（见验收标准），不作为发布物 |

**第一版只出 Windows x64 单平台**。用户环境是 Windows 10 Pro，没有第二个平台的需求；跨平台打包（macOS 需在 macOS 上构建、需开发者证书）属于独立需求。

### 2. ⚠️ 最大风险：打包可能让已有书架「凭空变空」，必须先解决

**这是本次唯一的真实技术风险，必须理解后再动手。**

`app.getPath('userData')` 的默认值是 `%APPDATA%\<app.getName()>`。而 `app.getName()` 返回 `package.json` 的 `productName`（若有），否则返回 `name`。

- **当前**：没有 `productName` → `app.getName()` = `local-novel-reader` → 数据在 `%APPDATA%\local-novel-reader\`
- **若为打包引入 `productName: "书页之间"`** → `app.getName()` = `书页之间` → **数据目录变成 `%APPDATA%\书页之间\`**

后果：用户现有书架（全部书籍记录、阅读进度、按书阅读设置）留在旧目录里，打包后的应用启动后**看到的是空书架**。文件并没有丢，但用户看到的现象就是「升级后我的书全没了」——而且这一现象在开发模式下同样会发生（`electron .` 也读 `package.json`），排查起来极具误导性。

**解决方案：在代码中显式固定数据目录，与产品显示名彻底解耦。**

在 `electron/main.js` 顶部（`app.whenReady()` **之前**）加入：

```js
// 数据目录名固定为 local-novel-reader，与产品显示名「书页之间」刻意解耦。
// app.getPath('userData') 默认跟随 app.getName()，而 app.getName() 跟随 package.json
// 的 productName——一旦让两者联动，改名或引入 productName 都会把老用户的 library.json
// 留在旧目录，表现为「升级后书架凭空变空」。显式 setPath 让开发态与打包态共用同一个目录。
const USER_DATA_DIR_NAME = 'local-novel-reader';
app.setPath('userData', path.join(app.getPath('appData'), USER_DATA_DIR_NAME));
```

这样开发态、打包态、以及未来任何改名，数据目录恒为 `%APPDATA%\local-novel-reader`，**零迁移**。取 `appData` 而非硬编码 `C:\Users\...\AppData\Roaming`，是为了不引入本机个人路径。

**注意**：即使不设 `productName`（保持 `local-novel-reader` 的显示名），也建议加这段——它把「数据目录」这个不该随手改变的东西固定下来，是对未来改名的保险。

### 3. 打包配置：写在 `package.json` 的 `build` 字段

**不新建 `electron-builder.config.js`。** 项目是 `"type": "module"`，独立配置文件需要处理 ESM 导出，而写进 `package.json` 的 `build` 字段没有这个问题，也少一个文件。

```json
"build": {
  "appId": "com.taxman2333.novelreader",
  "productName": "书页之间",
  "directories": { "output": "release" },
  "files": ["dist/**", "electron/**", "package.json"],
  "asar": true,
  "electronDownload": { "mirror": "https://npmmirror.com/mirrors/electron/" },
  "win": {
    "target": [{ "target": "zip", "arch": ["x64"] }],
    "artifactName": "novel-reader-${version}-win-x64.zip"
  }
}
```

逐项说明：

- **`productName: 书页之间`** —— exe 显示名与任务栏名称。**必须与第 2 节的 `setPath` 同时做**。
- **`files` 显式白名单** —— 产物只需要「构建好的前端 + 主进程代码」。这样 `tests/`、`docs/`、`.claude/`、`src/`（Vite 已把它打包进 `dist/`）、`项目规划方案.md`、`src/index.html`（已知冗余文件）都不会进包。`package.json` 是 electron-builder 的必需项，显式列出更清楚。
  - **依赖注意**：因为 `files` 被显式覆盖，`node_modules` 不再被自动纳入。当前主进程只用 Node 内置模块，**不需要任何运行时依赖**，所以是安全的。**若将来引入运行时依赖（非 devDependency），必须把 `node_modules/**` 加回 `files`**，否则打包后启动即报模块找不到。
- **`artifactName` 用 ASCII** —— 压缩包**文件名**保持 `novel-reader-1.0.0-win-x64.zip`，而包**内部的** exe 仍叫 `书页之间.exe`。理由：含中文的文件名在部分解压工具与下载链路上有编码风险（CP437/GBK 误判导致乱码），ASCII 文件名避开这个坑，同时不影响用户实际使用的 exe 名称。
- **`directories.output: "release"`** —— 与 `.gitignore` 中已有的 `/release/` 规则一致，产物不会被提交。
- **`asar: true`** —— 默认值，显式写出。
  - ⚠️ **需知悉**：`app.asar` 是可解开的，里面的 JS 能被提取阅读。本项目没有密钥、没有收费逻辑，无实际风险；但由此确立一条约束——**以后不要在源码里写死任何敏感值**（这本来就与核心约束 4/6 一致）。
- **`electronDownload.mirror`** —— 见下节。

### 4. 网络：本机 `github.com` 被阻断，必须配镜像

electron-builder 默认从 **github.com** 下载 Electron 二进制与工具链，本机该域名被阻断，**不配镜像会直接打包失败**。

已实测：`npmmirror.com` 可达（HTTP 302），本机 npm registry 本就指向 `registry.npmmirror.com`。

**方案：新增仓库级 `.npmrc`（会提交进 Git，可复现，不依赖任何环境变量）**

```ini
electron_mirror=https://npmmirror.com/mirrors/electron/
electron_builder_binaries_mirror=https://npmmirror.com/mirrors/electron-builder-binaries/
```

- 只写这两条**二进制镜像**，**不写 `registry=`**——npm 源在本机已全局配置好，仓库级再写一遍只会造成两处真相。
- `.npmrc` **不含任何凭据、不含个人路径**，可以安全提交。
- 第二行是必需的：Windows 上 electron-builder 默认用 `rcedit`（来自 `winCodeSign` 包）改写 exe 的图标与版本信息，该工具链同样从 github.com 拉取。
- `electronDownload.mirror` 与 `.npmrc` 的 `electron_mirror` 二者**保留其一即可**；两处都写是有意的冗余——`.npmrc` 覆盖 `@electron/get` 的直接下载路径，配置字段覆盖 electron-builder 自身的下载路径。实施时若发现其中一处未生效，另一处可兜底。

**首次打包会下载约 200MB+ 工具链**（Electron 32.3.3 win32-x64 zip、winCodeSign、以及用于压缩的 7za）。当前 `%LOCALAPPDATA%\electron-builder\Cache` 为空，第一次会明显慢，属正常现象，不是卡死。

### 5. 新增 npm 脚本

```json
"dist": "npm run build && electron-builder --win"
```

**命名为 `dist` 而非 `release`**：仓库里已有 `.claude/skills/release/` 这个 Skill，脚本名重复会造成「`npm run release` 是跑打包还是走发布流程」的歧义。

### 6. 发布 Release

打包产物本身**不进 Git**（`.gitignore` 已忽略 `/release/` 与 `*.zip`），只作为 Release 附件上传。

```bash
gh release create v1.0.0 "release/novel-reader-1.0.0-win-x64.zip" \
  --title "v1.0.0 — 书页之间" \
  --notes-file <发行说明> \
  --repo taxman2333/novel-reader
```

- 走 `gh`（`api.github.com` 与 `uploads.github.com` 均已实测可达），**绕开被阻断的 `github.com:443`**，不需要代理。这与 `git push` 必须走代理的情况不同。
- `gh release create` 会自动建 tag `v1.0.0`。**这一步需要用户明确授权**——`/implement` 与 `/github` 两个 Skill 都禁止自动创建 tag 与 Release，因此实施阶段只做到产出 zip 为止，发布单独确认。

**发行说明应包含**（这是打包暴露出来、用户需要知道的事，不是缺陷）：

> 书架数据保存在 `%APPDATA%\local-novel-reader\`，**不随本压缩包移动**。把应用拷到另一台电脑后书架会是空的；且书架记录保存的是小说文件的**绝对路径**，即使手动复制 `library.json` 过去，路径对不上也打不开书。这是「小说正文不复制到应用内部、只记录原文件路径」这一设计的必然结果。

## 潜在风险

| 风险 | 应对 / 验证方式 |
|---|---|
| **数据目录位移导致书架变空** | 最高风险。对策见技术方案第 2 节；验证见验收标准 4、5——**必须实际看到打包后的应用列出已有书籍才算通过** |
| 镜像不生效导致打包失败 | 双保险：`.npmrc` + `build.electronDownload.mirror`。失败时报错会明确指出正在从哪个 URL 拉取，据此判断哪一层没生效 |
| 首次打包下载量大、耗时长 | 预期行为。缓存写入 `%LOCALAPPDATA%\electron-builder\Cache`，第二次起显著加快 |
| 产物过大且压缩率低 | Electron 运行时本身约 200MB，压缩后约 80–100MB，属该技术栈的正常量级。若需进一步减小，可调 `compression: "maximum"`（耗时换体积），或另开「按需裁剪 locale」的独立需求 |

### 实施中发现的、方案未预见的问题

**`electron` 原本被放在 `dependencies`，electron-builder 直接拒绝打包。**

首次 `npm run dist` 失败，报：

```
⨯ Package "electron" is only allowed in "devDependencies".
  Please remove it from the "dependencies" section in your package.json.
```

方案第 3 节只考虑了 `files` 白名单会排除 `node_modules`，**没有料到依赖归类本身就不合规**。已把 `electron` 移到 `devDependencies`——这是正确归类，打包产物自带 Electron 运行时，不依赖 npm 装的那个包。`npm run dev`、`npm test`、`npm run test:ui` 均不受影响（devDependencies 默认安装）。

顺带记录一个观察：`release/` 下 electron-builder 26 生成的是 `builder-debug.yml`，而 `.gitignore` 里写的是旧名 `builder-effective-config.yaml`。**不影响结果**——两者都在 `/release/` 目录内，已被该规则覆盖（`git check-ignore` 实测确认）。
