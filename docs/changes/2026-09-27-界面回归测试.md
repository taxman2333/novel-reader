# 建立界面回归测试

## 需求描述

为项目建立一套**界面级回归测试**，用于固定住那些纯逻辑单元测试无法覆盖、且已经真实出过问题的界面行为。

明确范围（本次只做第一层）：

- 让真实的渲染代码（`src/main.js`、`src/reader.js`、`src/styles.css`）在一个**隐藏的 Electron 窗口**中运行。
- 在 `window.novelApi` 这一层替换为测试替身，**不修改任何业务代码**，不引入任何新依赖。
- 用 `webContents.executeJavaScript` 读取真实 DOM 几何与计算样式，对以下行为做断言：工具栏固定、阅读设置持久化、四种主题切换、阅读进度保存与恢复、空书架导入入口、`novelApi` 接口形状。

**不在本次范围**：驱动真实 `electron/main.js`、真实文件读写与真实 `library.json` 的端到端测试（第二层），详见「技术实现方案」中的说明。

## 需求背景

`docs/ROADMAP.md` 第四节「工程能力建设」已列出三项缺失能力：界面级自动化测试、Electron 集成测试、布局回归检查。

这个缺口已经造成了实际损失。开发过程中出现的两个最影响使用体验的 Bug：

1. **阅读区工具栏随正文滚动消失**——`src/styles.css` 的布局问题；
2. **单本小说的阅读设置重新打开后丢失**——`src/main.js` 的 `persistLibrary()` 与 `activeBook` 对象身份问题。

这两个问题**在原理上就超出了当前 12 项单元测试的覆盖能力**：它们不是函数逻辑错误，而是「布局是否成立」「对象引用是否仍然指向同一份数据」「保存载荷里到底写了什么」。当时只能靠在临时脚本里创建隐藏窗口、实测 `getBoundingClientRect()` 与保存载荷才发现。那些脚本是临时的，**没有纳入仓库**，也无法在后续改动中自动重跑。

结果是：任何人（包括未来的自己）再动一次 `styles.css` 或 `persistLibrary()`，这两个问题都可能原样复发，而且不会有人立刻发现。

需要强调的是：**这套测试的价值不在于提高覆盖率数字，而在于把已经伤过的三个具体位置钉死。**

### 布局事实（决定断言怎么写）

`src/styles.css:61` 与 `:72`：

```css
.reader-shell { height: 100vh; overflow: hidden; display: flex; flex-direction: column; }
.reader-scroll { flex: 1; min-height: 0; overflow: auto; scroll-behavior: smooth; }
```

这条规则在测试中可以直接利用，见下文。

## 变更原因

不改的话，界面行为只能人工验证，而这已经被证明会漏：

- 人工验证依赖「碰巧试到那一步」。工具栏消失要滚动到一定距离才明显，设置丢失要退出重进才发现。
- 没有自动重跑机制。改动 CSS 或保存逻辑后，旧问题复发不会被发现。
- 临时脚本不可复用，每次都要重新写一遍，且容易写出**会误报的脚本**——调试过程中就出现过一次因 mock 状态放在 preload 模块内存里、每个窗口重新实例化而导致的假失败。

## 技术实现方案

### 总体结构

```
npm run build                          # 先构建，让测试跑在真实产物上
  └─ electron tests/ui/entry.mjs       # 测试专用主进程入口
       ├─ 注册 mock:* IPC 处理器（假数据存在主进程）
       ├─ 创建隐藏 BrowserWindow，preload 指向 mock-preload.mjs
       ├─ 加载 dist/index.html         # 真实构建产物
       ├─ 依次执行 specs.mjs 中的断言
       └─ 输出结果并以退出码结束
```

### 关键决策

**决策一：用 Electron 自带的 `executeJavaScript`，不引入测试框架。**

Electron 已经提供了创建窗口、执行脚本、读取返回值的能力。引入 Playwright 或 Puppeteer 属于 `CLAUDE.md` 明确反对的「为实现简单功能引入不必要的复杂依赖」，且会带来一整套独立于 Electron 的版本兼容问题。

**决策二：测试入口是独立的 `tests/ui/entry.mjs`，不是 `electron/main.js`。**

`electron <路径>` 可以指定任意入口文件，绕过 `package.json` 的 `main` 字段。这样测试主进程可以自由注册 mock 处理器，而**生产代码一行都不用动**。

**决策三：假数据存在测试主进程，不放在 preload 模块里。**

这一条是硬性的。preload 模块的内存**在每个窗口实例化时都会重置**。之前调试时正是把 mock 状态放在 preload 中，导致第二个窗口读到了硬编码初始值而不是第一个窗口保存的值，产生了一次假失败。状态放在主进程后，`webContents.reload()` 后依然存在——这也让「重启应用后设置是否还在」可以被真实验证。

**决策四：测试跑在 `dist/` 构建产物上，而不是 Vite 开发服务器。**

- 结果确定，不需要与 Vite 的启动时序竞争；
- 顺带验证了**生产构建产物能正常启动**——这条路径平时只在发布时才被走到，本身就是风险点（历史上 ESM preload 相关的问题就出在这条路径上）。

代价是每次要先跑一次 `npm run build`，可接受。

**决策五：只断言语义，不断言像素。**

断言「工具栏 `top` 等于 0」「主题变量等于 `#2d302f`」「顶部段落索引等于保存值」，而不是断言具体高度、间距、滚动像素。后者会在任何一次合理的排版微调后误报——那会迅速让测试失去可信度从而被忽略。

### 确定性措施（针对已知的翻车点）

| 问题 | 措施 |
|---|---|
| `scroll-behavior: smooth` 导致读取 `scrollTop` 恒为 0 | 主用 `app.commandLine.appendSwitch('force-prefers-reduced-motion')`；并在每次进入阅读页后把 `#reader-scroll.style.scrollBehavior` 显式设为 `'auto'` 兜底。这与产品在 `prefers-reduced-motion` 下的行为一致，不是绕过测试 |
| 隐藏窗口的后台节流导致 500ms 防抖定时器不按时触发 | `webPreferences: { backgroundThrottling: false }`。**不加这条，进度保存测试会随机失败** |
| 隐藏窗口几何量读出 0 | 优先 `show: false`（`paintWhenInitiallyHidden` 默认为 true，会正常布局）。若读到 `offsetHeight === 0`，回退为 `show: true` + 窗口移到屏幕外 |
| 固定 `sleep` 造成的偶发失败 | 一律使用 `waitFor(条件, 超时)` 轮询，不使用固定等待 |
| 测试进程卡死 | 主进程加 60 秒看门狗，超时以退出码 2 结束 |
| 断言失败难以定位 | 失败时输出当时的 DOM 快照与相关变量值，而不是只报一行 assert |

### 断言清单（7 条）

| # | 名称 | 断言内容 | 对应问题 |
|---|---|---|---|
| 1 | `api-surface` | `Object.keys(window.novelApi)` 与预期列表完全一致 | 防止 mock 与真实 preload 漂移 |
| 2 | `shelf-empty` | 空书架渲染出 `#empty-import`，且点击后触发了一次 `chooseBook` | 此前漏绑该按钮事件 |
| 3 | `import` | mock 的 `chooseBook` 返回文件后，书架出现该书并自动进入阅读页 | 导入主流程 |
| 4 | `toolbar-fixed` | 滚动后 `.reader-toolbar` 的 `top` 仍为 `0` | **Bug 1 回归** |
| 5 | `theme-switch` | 依次点击四种主题，`.reader-shell[data-theme]`、`--reader-bg` 计算值、`documentElement.dataset.theme` 三者同步变化 | 主题未完整应用 |
| 6 | `settings-persist` | 改字号后，① mock 收到的保存载荷中 `books[i].settings.fontSize` 为新值；② `reload()` 冷启动后重新打开该书，字号仍是新值 | **Bug 2 回归** |
| 7 | `progress-persist` | 滚动 → 等待防抖保存 → 返回书架 → 重新打开，恢复后的顶部段落索引等于保存的 `paragraphIndex` | 进度恢复 |

#### 两条断言的关键细节

**第 4 条必须加防空转判断。** 如果合成文本太短，滚动会被截断，此时工具栏当然在顶部——测试会因为错误的原因通过。因此顺序必须是：先断言 `scrollTop` 确实达到了目标值，再断言工具栏位置。

**第 6 条必须同时断言保存载荷和冷启动结果。** 只断言「返回书架再打开，字号还在」是不够的：`library` 变量在渲染进程中一直存在于内存，即使 `saveLibrary` 完全失效，这一步也会通过。必须检查 mock 实际收到的保存载荷，再通过 `reload()` 验证冷启动。**冷启动这一步恰好是当初那个 Bug 的真实形态**——`persistLibrary()` 调用 `normalizeLibrary()` 会重建书籍对象，使 `activeBook` 与 `library.books[i]` 脱钩，保存出去的载荷里 `settings` 仍是 `null`。

**第 7 条不能比较滚动像素。** `restoreScroll()` 用 `scrollIntoView({block:'start'})` 把目标段落对齐到顶部，恢复后的 `scrollTop` 天然不等于保存前的 `scrollTop`。因此断言的是**顶部段落索引**。

#### 合成测试文本的硬性要求

mock 返回的文本由测试进程按确定性规则生成，不落盘。有一条容易忽略的约束：

**每段的前 80 个字必须互不相同。**

原因是 `src/reader.js:39` 的 `findRestoreIndex()` 优先按上下文匹配：

```js
const contextIndex = paragraphs.findIndex(({ text }) => text.includes(progress.context.slice(0, 80)));
```

如果段落开头重复（例如循环生成的「第一章」），匹配会命中**错误的段落**，测试将以难以理解的方式失败。生成器需保证每段在前 80 字内包含唯一标识。

同时，文本长度需保证在默认设置（字号 18、行高 1.9、版心 720）下可滚动超过 4000px，约 200 段即可。

### 被否决的替代方案

| 方案 | 否决原因 |
|---|---|
| Playwright / Puppeteer | 不必要的依赖；Electron 自带能力已足够 |
| jsdom + 断言 DOM 字符串 | 不加载真实 CSS，恰好测不到「布局是否成立」——而那正是最需要覆盖的部分 |
| 快照测试（截图对比） | 在 Windows 上受缩放、字体渲染影响，误报率高，维护成本超过收益 |
| 用 Vite 开发服务器 | 增加启动时序竞争，收益不明显 |
| 直接驱动 `electron/main.js` | 需要解决原生文件对话框无法自动驱动的问题，属于第二层内容 |
| 为测试在生产代码里加环境变量开关 | 生产代码里多一个测试专用分支，本次没有必要 |

### 关于第二层（本次不做）

第二层指：驱动真实 `electron/main.js`，使用真实文件读写与真实 `library.json`。

技术上可行且**不需要改业务代码**——可用 Electron 原生的 `--user-data-dir=<临时目录>` 参数让 `app.getPath('userData')` 指向隔离沙盒，再预置一份 `library.json`，从而绕开无法自动驱动的原生文件对话框。

**本次不做**，理由：

- 第二层相比第一层独有覆盖的只有「真实文件读取 + 真实 JSON 落盘」，而这两块**已有单元测试覆盖**（`tests/book-service.test.js`、`tests/library-store.test.js`）；
- 它会引入新的不稳定来源（跨进程启动、临时目录清理、端口与调试协议）；
- 等真正开始做「章节目录」时再做，那时阅读器数据流会大改，收益才明显。

本次在 `docs/ROADMAP.md` 中保留该方向，不实现。

## 潜在风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 隐藏窗口几何量读数为 0 | 布局断言全部失效 | 检测到 `offsetHeight === 0` 时回退为屏幕外可见窗口 |
| 后台节流导致防抖定时器不触发 | 进度测试随机失败 | 必须设置 `backgroundThrottling: false` |
| mock 与真实 preload 漂移 | 测试通过但真实应用已坏 | 第 1 条 `api-surface` 断言；`mock-preload.mjs` 顶部注释指向 `electron/preload.mjs` |
| 断言写得过细导致误报 | 测试被忽略，失去意义 | 只断言语义，不断言像素；失败时输出 DOM 快照便于判断是误报还是真问题 |
| 本机 `node_modules/electron` 安装损坏 | 测试与应用一起无法启动（该问题在本机历史上出现过：Electron 32 自带的解压库在 Node 24 下会静默中断，`electron.exe` 缺失） | 启动前检查 `node_modules/electron/path.txt` 与 `electron.exe` 是否存在，缺失时给出明确可执行的提示，而不是抛出难以理解的错误 |
| Electron 启动失败或测试卡死 | 命令挂起 | 60 秒看门狗，超时以退出码 2 结束 |
| 测试成为维护负担 | 后续改动不愿跑 | 控制在 5 个文件、7 条断言；配套 `tests/ui/README.md` 说明如何扩展 |

**回退方式**：本方案不修改业务代码。如需回退，删除 `tests/ui/` 目录并从 `package.json` 移除 `test:ui` 脚本即可，不留残留。

## 验收标准

1. `npm run test:ui` 能完成运行，输出 7 条断言的结果，全部通过时退出码为 `0`。
2. **反向验证（必做，这是判断测试是否真实有效的前提）**：
