## 一、补齐 v1.0.0 方案中尚未落地的内容

这些是 v1.0.0 方案已提出、但当前代码尚未实现的部分，优先级高于全新功能。

### 1.1 手动编码选择入口

- **来源**：方案 5.1「如果无法可靠识别编码，应提供编码选择或重新读取入口」
- **现状**：仅自动检测（UTF-8 → GB18030 回退），检测失败时无人工干预手段
- **价值**：解决罕见编码 TXT 无法阅读的问题
- **需要评估**：是否只在解码出现替换字符时提示，还是始终提供入口

### 1.2 Electron 打包分发

- **来源**：方案阶段五「完成打包运行」
- **状态**：**已完成**（2026-09-27）。见 `docs/changes/2026-09-27-打包与发布Release.md`
- **结果**：`npm run dist` 产出 `release/novel-reader-<version>-win-x64.zip`（Windows x64 免安装目录版，约 105MB），可作为 GitHub Release 附件分发。选型过程与被否决的替代方案记录在该方案文件中

### 1.3 应用图标

- **来源**：打包分发的后续项（v1.0.0 沿用 Electron 默认图标，作为已知限制记在发布说明里）
- **状态**：**已完成**（2026-09-28）。见 `docs/changes/2026-09-28-应用图标接入.md`
- **结果**：设计并接入自定义图标，exe 与窗口均使用。图标源文件、三个备选方案、生成脚本与设计说明见 `design/app-icon/`
- **备注**：接入时**没有**走 electron-builder 默认的 `build/icon.ico`——本仓库 `.gitignore` 有根锚定的 `/build/` 规则，放进去会被静默排除。改用显式路径 `design/app-icon/final/icon.ico`

**后续可再评估**：NSIS 安装程序、macOS/Linux 打包、自动更新。这几项都不是 v1.0.0 方案的要求，属独立需求。

### 1.4 大文本渲染优化

- **来源**：方案 5.3「避免在界面中重复创建过多 DOM 节点……必要时采用分页或虚拟滚动」
- **状态**：**已完成**（2026-09-28）。阶段 1（低风险改动）与阶段 2（段落窗口化渲染）均已落地
- **结果**：DOM 里始终只有视口附近的约 401 段，屏幕外由垫片撑高。改一次字号/版心宽度实测 79k 段 691.6→6.8 ms、134k 段 869.4→5.0 ms（基准的同步排版部分）
- **已定的取舍**（2026-09-28 评估完成）：选**窗口化渲染 + 段落偏移表**，不选纯 `content-visibility: auto`。理由：后者屏幕外段落只能用估算高度，`scrollIntoView` 会落在估算位置，**「记住你读到哪」这个核心功能会失准**
- **方案与实测数据**：`docs/changes/2026-09-28-阅读性能优化.md`
- **回归工具**：`npm run bench`（`tools/bench-reader.mjs`）+ 界面回归的 `windowing` 用例
- **遗留**：打开/导入的端到端耗时、滚动体感、5×2 次恢复位置往返**须由用户实测确认**（基准与自动化测试都无法替代）。实测口径与测量边界见方案文档

### 1.5 异常处理补全

- **来源**：方案第 10 节，部分场景当前只冒泡为通用提示
- **待补**：保存进度/配置失败、文件被其他程序锁定、没有读取权限
- **价值**：满足方案「每种异常都应提供可执行的下一步」

### 1.6 用户反馈中尚未定位的两条

用户 2026-09-28 反馈五条，第 2/3/5 条（导入慢、再次打开慢、改设置卡顿）已由 1.4 解决；以下两条**仍未定位**，
且**不能靠改代码猜**，必须先在你的机器上测量。

- **启动慢（第 1 条）**：已排除应用代码——相对空白 Electron 只慢 2～6 ms。怀疑对象是未签名 186 MB exe 的
  Windows Defender/SmartScreen 扫描或冷文件缓存。**下一步**：在 `electron/main.js` 各阶段打时间戳，
  或用 Windows 性能分析器确认耗时落在进程启动之前还是之内。
- **滚动卡顿（第 4 条）**：合成基准原先未能复现；改用**真实 `src/styles.css`** 后复现出书 B 帧间隔中位数
  29.6 ms（约 34 fps），窗口化后回到 5.5 ms。但这仍不是端到端测量，**是否真的改善必须由你实测判定**。
  **下一步**：修复前后各滚一次同一本书对比；若仍卡顿，用 DevTools Performance 录制一次滚动，
  看时间花在合成、脚本还是绘制上。
- **关联**：两条的实测口径与验收标准见 `docs/changes/2026-09-28-阅读性能优化.md` 验收标准第 5、7 条

## 二、方案中列出的扩展方向

来自 v1.0.0 方案第 13 节，方案明确要求「不应提前加入第一版」。

按方案原文顺序：

- [ ] 可选的便携版配置目录

**后续可再评估**：识别规则目前是启发式的（锚定段首 + 尾部限长 + 数字序列递增检查）。若遇到漏判较多的真实小说，可考虑按书籍记忆用户的识别偏好或提供手动纠正入口，但那是独立需求，不在本次范围内。

## 六、推进方式

新需求统一走：

```
/change <需求>  →  生成变更方案  →  确认  →  /implement  →  测试  →  更新文档  →  commit  →  /github
```

较小的修改可直接进行。只有影响**功能、架构、数据结构或用户体验**的改动才需要完整流程。
