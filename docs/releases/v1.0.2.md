一个只服务于个人的本地 TXT 小说阅读器。**完全本地运行**：不接入服务器、账号或云同步，不上传小说文件或阅读数据。

## 下载与使用

下载下方的 `novel-reader-1.0.2-win-x64.zip`，解压后双击 `书页之间.exe`。

**不需要安装 Node.js。** 这是免安装版：不写注册表、不装进 `Program Files`，卸载就是删掉解压出来的文件夹。仅提供 Windows x64 版。

## 这个版本改了什么

**四件事：阅读性能优化（两个阶段）、阅读页滚动条改为自绘、章节标题排版，以及一条项目约束的调整。** 前两件是本次的主要工作。

### 一、阅读性能优化

针对实际体验里最难受的几处逐个定位。定位结果里有一条很重要：**「exe 启动要等几秒」不在应用代码里**，详见下面的「已知限制」。

**阶段 1（应用层）**

- **恢复阅读位置改为瞬时跳变**：原先用的是平滑滚动，跳转必须跑完整个动画。实测同一本书同一次恢复——平滑 **924 ms** 才停、**206 ms** 后才出现第一次可见移动；瞬时 **41.5 ms**。**打开一本书因此快约 0.9 秒。**
- **阅读设置按帧应用 + 落盘防抖**：拖滑条时同一次拖动里的多个事件合并为每帧一次样式写入，松手时取当前值（快速拖动不会停在中间态），设置落盘防抖 400 ms。**字号、行距、段距、版心宽度这些滑条现在是跟着手走的。**
- **滚动定位不再每帧重建段落列表**，段落列表在正文建树后取一次并缓存。
- **启动时书架先渲染、再检查文件可用性**，不再等 N 次磁盘往返才能显示书架。
- **修掉一个会丢数据的缺陷**：旧实现里「退出时的最后一次保存」起个头就放行退出，实测在数据目录里抓到了残留的 `library.json.tmp`。现在写入串行化，并在所有窗口关闭之后才真正退出。

**阶段 2（渲染架构）**——这是滚动卡顿的根因

- **正文不再整本渲染为 DOM，改为「段落窗口 + 上下垫片」**：DOM 里始终只有视口附近的 **401 段**，屏幕外的部分由两块垫片撑出高度；段落偏移由一张前缀和表给出，屏幕外先用字数估算高度、渲染后再回填实测值。

实测数字（`npm run bench`，可重跑；不含 Electron IPC 与窗口重建那一下）：

| 场景 | 优化前 | 优化后 |
|---|---|---|
| 改一次字号（7.9 万段） | 691.6 ms | **6.8 ms** |
| 改一次版心宽度（7.9 万段） | 713.8 ms | **3.4 ms** |
| 改一次字号（13.4 万段） | 869.4 ms | **5.0 ms** |
| 改一次版心宽度（13.4 万段） | 881.2 ms | **2.8 ms** |
| 滚动帧间隔中位数（13.4 万段） | 29.6 ms | **5.5 ms** |

### 二、阅读页滚动条改为自绘

长书上原生的右侧滚动条是**不可用的**：一本 7 万段的书文档高 610 万 px，滑块按比例只有 **0.10 px**，Chromium 按最小长度兜底画成顶端约 10px 的一小截。结果是拖动 1px ≈ 8000px 正文 ≈ 10 屏，轻微一动就按比例飞到最下方；而按在空白轨道上（滑块只有 10px，点击几乎必定落空）Chromium 会朝按下方向持续翻页、按住不停——看起来正是「自己滑到底、再往上拖也不动了」。

改为自绘一条覆盖在正文右侧的滚动条：

- **滑块长度有 24px 下限**，永远抓得住；整本装得下一屏时整条隐藏。
- **拖动按全书比例定位**，与目录面板的进度滑条是同一套换算。
- **点空白轨道翻一屏**，**滚轮落在轨道上转发给正文**。
- **滚轮、方向键、PageUp/Down、空白键保持原生 1:1 手感不变**；用过滚动条之后键盘翻页照常有效。

### 三、章节标题排版

目录识别出的标题段落在正文里放大到正文的 **1.3 倍并居中**（此前与正文同字号、左对齐）。

顺带修掉一处取整导致的落点漂移：跳章节时落点偶尔会比目标低约 1px，视口顶部就退到上一段。同一类风险还有一个入口是「改字号之后不知道读到哪了」，本次一并收敛。

### 四、一条项目约束的调整

原有的「小说正文**不复制**到应用内部、不保存到应用数据库」放宽为：整本正文仍然不复制、原文件始终是唯一权威来源，但**为功能所必需**保存**有限的正文片段**与由正文派生的短字符串——也就是阅读位置恢复用的 240 字「附近文本」与章节标题——是允许的。

**这不改变任何行为**：那 240 字自 v1.0.0 起就一直在保存，本次只是把既有行为写进约束文本，不再让实现与文档互相打架。边界仍然是「片段」。

## 升级说明

**书架数据完全不受影响。** `library.json` 没有结构变化、不需要迁移，数据仍在 `%APPDATA%\local-novel-reader\`。

直接解压新版本覆盖旧文件夹即可，已导入的书、阅读进度、阅读设置全部照常。

## 需要知道的两件事

**一、书架数据不随这个压缩包移动。** 它保存在 `%APPDATA%\local-novel-reader\`。

**二、书架记录保存的是小说文件的绝对路径。** 把应用拷到另一台电脑后，即使一并复制了书架数据，路径对不上也无法打开原书。这是「小说正文不复制到应用内部、只记录原文件路径」这一设计的必然结果，不是缺陷。

## 已知限制

- 仅打包 Windows x64；无安装程序、无自动更新。
- **「启动要等几秒」本次没有解决，因为它不在应用代码里。** 实测本应用的完整启动路径相对一个空白 Electron 应用只慢 **+2～6 ms**——窗口、IPC、菜单、`dist` 加载都不是瓶颈。剩余时间最可能来自 Windows Defender / SmartScreen 对**未签名的 186 MB 可执行文件**的每次启动扫描，以及冷文件缓存。这两条都需要在具体机器上定位，也都不是改应用代码能解决的。本次只做到「书架先渲染、不再等文件可用性检查」。
- **自绘滚动条的拖动是粗调**：610 万 px 的书上 1px 轨道 ≈ 10 屏，精细定位仍靠滚轮与章节目录。
- **章节标题的 1.3 倍率是固定的**，不随字号设置单独调节。
- **导入与打开的超长篇耗时仍以文本流水线为主**（解码 → 规范化 → 分段 → 章节识别，实测约 1.2 s），本次只做掉其中一处重复归一化（gb18030 解码 24.9 → 16.4 ms），其余未触及。
- 四个背景主题下新标题排版的观感由使用者在真机确认，界面测试覆盖不到「好不好看」。
