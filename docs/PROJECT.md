## 1. 项目定位

一款**服务于个人使用的本地 TXT 小说阅读器**。用户从电脑中选择 `.txt` 小说文件导入，应用记录原文件位置和必要元数据；以后打开应用时，根据记录的路径读取原文件并继续阅读。

界面使用网页技术构建，以本地桌面应用形式运行。不依赖服务器、账号或云服务，整本小说正文不复制到应用内部，原文件始终是唯一权威来源。

## 3. 核心约束（已确定，未经明确决策不得更改）

以下来自 v1.0.0 方案，属于**已确定的项目要求**，不是可随意调整的实现细节：

1. **整本小说正文不复制**到应用内部，原文件始终是唯一权威来源。**不允许**：把整本正文写入 IndexedDB、应用数据库或应用专用目录；不允许用应用内的副本替代原文件。**允许**（2026-09-28 用户明确决策后放宽）：为功能所必需保存**有限的正文片段**与由正文派生的短字符串，例如阅读位置恢复用的「附近文本」（约 240 字）、章节标题；这类内容可以落入 `library.json`。**放宽的理由**：本应用只服务于个人、只在本机运行，这些片段不涉及隐私风险。**边界仍是「片段」**：任何要保存正文的地方都必须先说明为什么必需、以及为什么不能用索引或元数据代替。
2. 应用保存**原始文件绝对路径**与必要元数据，小说始终由用户自己保管。
3. **删除书架记录与删除原始文件必须是两个独立动作**。第一版不提供删除原始文件的功能。
4. 项目**默认优先保持本地运行**：不接入服务器、账号、云同步、远程数据库。
5. 文件系统能力必须与渲染界面分离，由受控的桌面端接口提供；页面脚本不得直接获得系统权限。
6. 应用**不上传文件内容、不启动网络服务、不发送使用数据**。
7. 不得擅自增加第一版没有要求的功能（账号、在线书库、云同步、社交、广告等）。
8. 读取失败必须给出**具体原因**，而不是通用错误提示。

## 4. 已实现功能（真实状态）

### 4.1 文件导入

- 通过系统文件选择器（`dialog.showOpenDialog`）导入，过滤器限定 `txt`。
- 只接受 `.txt`，非 `.txt` 会返回明确错误。
- 空文件会返回「这个 TXT 文件没有可阅读的内容」。
- 导入只建立文件引用，不移动、不复制、不修改原文件。
- 重复导入同一路径时，直接打开已有记录，不产生重复条目。

### 4.2 编码处理（真实实现）

`electron/book-service.js` 的 `decodeText()` 按以下顺序判定：

1. `FF FE` 开头 → UTF-16LE
2. `EF BB BF` 开头 → UTF-8（含 BOM）
3. 按 UTF-8 解码后统计替换字符 `�` 数量，为 0 则判定 UTF-8
4. 否则回退 GB18030

### 4.3 书架

- 展示书名、上次阅读时间、阅读进度百分比。
- 按最近打开时间倒序排列。
- 显示原文件不可用状态，并提供「重新定位」。
- 支持从书架移除记录（`window.confirm` 明确说明不会删除原文件）。
- 无小说时显示空状态引导。

### 4.4 阅读器

- 工具栏固定在顶部，**不随正文滚动**（正文区独立滚动）。
- 工具栏为三栏布局，从左到右：**左导航区**（返回书架 `←`、目录按钮「目录」）、**中部书名与阅读进度**、**右操作区**（阅读设置 `Aa`）。
- 底部有细进度条。
- 正文按段落渲染为 `<p data-paragraph-index="n">`，**只渲染视口附近的约 401 段**（`createParagraphWindow`，见第 4.4.1 节）；屏幕外的部分由上下两块 `.reader-spacer` 撑出高度，DOM 里不会有第二份正文。
- **章节标题**（目录识别出来的那些段落）渲染为 `<p class="reader-chapter">`：字号是正文的 1.3 倍（`CHAPTER_SCALE`，与 `src/styles.css` 同源）且**居中**，因此没有段首缩进——`text-indent` 会把居中后的那一行往右推。类名由窗口在 `paint()` 里按章节段落序号加上，屏幕外段落的高度估算也跟着换字号（见第 4.4.1 节）。
- 视口顶部所在段落由**偏移表二分查找**得出（`topIndex()`），滚动期间不再对 DOM 做节点列表构造或二分查找。
- **段落分隔自动适配两种 TXT 格式**：先统计空行占比，≥ 0.15 时按空行分段，否则按单个换行分段。只按空行切会把「一行一段、没有空行」的文件（网文抓取版常见）解析成一整个段落，整本渲染成单块文字；只按换行切会把空行分段文件里本来就有软换行的段落切碎。

### 4.4.1 段落窗口化渲染（`src/reader.js` 的 `createParagraphWindow`）

整本书一次性物化成 DOM 时（实测 13.3 万段、文档高 1130 万 px），任何触及全篇几何的操作都要 0.5～1.0 s。
现在 DOM 里始终只有视口附近的 `2×200+1 = 401` 段，屏幕外由垫片撑高。

三样东西构成它：

1. **段落高度估算**（`estimateParagraphHeight`）：按「一行放得下几个字」推算占几行，
   乘行高再加段间距。公式里的常量与 `src/styles.css` 绑死：`letter-spacing .015em`、段首缩进 `2em`、
   章节标题的字号倍率 `CHAPTER_SCALE = 1.3`（标题不缩进，段间距是 `em`，跟着放大后的字号走）。
2. **偏移表**（`buildOffsetTable`）：段落序号 → 文档坐标的前缀和，`Float64Array`，长度 N+1。
   `offsets[0]` 是正文内容盒顶（实测 `padding-top`，**不写死数值**），因此 `offsets[i]` 可以直接与 `scrollTop` 比较。
3. **窗口管理**（`paint`）：建窗口 → 用相邻兄弟 `offsetTop` 之差**回填实测高度**（行高、段间距、
   标点压缩、中英文混排的差异全在里面）→ 重建表 → 设垫片高度 → 把锚点设回原位。

两个不显眼但必需的机制，都对应一次实测到的跳位：

- **锚点**（`anchorIndex` + `anchorViewportOffset`）：重建前记下「视口顶部那一段」及其被卷上去的像素数，重建后钉回原处。
  采锚点**只查偏移表、不读 DOM**——改字号时样式已经改掉，那一刻读到的元素位置反映的是「旧 `scrollTop` + 新字号」，
  实测会让整本书往回跳 **101 段**。
- **半像素容差**（`OFFSET_EPSILON = 0.5`）：表里是浮点高度，`scrollTop` 按设备像素取整，边界反查会提前落一段（实测 1 段）。
- **写入后再核对一次**（`paint()` 末尾）：读侧的半像素容差挡不住写侧的一整像素。`scrollTop` 由浏览器取整
  （实测是向下取整），目标值的小数部分大时落点会比目标低近 1px，视口顶部就退到上一段——实测过一次：
  章节标题改字号后跳到第 150 章的落点从第 3150 段退成第 3149 段。写完读回来核对，退段就补 1px。

`.reader-scroll` 上的 `overflow-anchor: none` 是第三处必要设置：Chromium 的滚动锚定会在垫片高度变化时自己调
`scrollTop`，与偏移表打架。

**定位方式**：不再有 `scrollIntoView`。`scrollToIndex(i)` 把第 i 段对齐到视口顶部（该段恒为窗口中心，因此必定被实测校正过）；
`getProgressFromScroll` 传入偏移表时直接查表，不用「比例 × 段落数」估算——后者在段落长度不均时会偏出十几章（第 9 节第 7 条）。

**未采用的替代方案**（理由见变更方案）：`content-visibility: auto`（屏幕外只有估算高度，
`scrollIntoView` 会落在估算位置，「记住你读到哪」会失准）、按章节整块渲染（改变跨章连续滚动的交互）、
把正文缓存到磁盘（违反核心约束 1，用户 2026-09-28 已决策不做）。

### 4.4.2 阅读页滚动条（自绘，`src/reader-scrollbar.js`）

**原生滚动条在长书上是不可用的**，因此阅读页把它整条隐藏（`scrollbar-width: none` 与
`::-webkit-scrollbar { width: 0 }`），换成自己画的一条。实测依据：

- 一本 7 万段的书在文档里是一比一铺开的，文档高 **6,098,611px**、视口 764px；滑块按比例只有
  **0.10px**，Chromium 只能按最小长度兜底，画出来是贴在轨道最顶端约 10px 的一小截（截图实测）。
- 于是拖动 1px ≈ 8000px 正文 ≈ **10 屏**：轻微一动，滑块就按比例飞到最下方；而按在空白轨道上
  （滑块只有 10px，绝大多数点击都会落空）Chromium 的行为是**朝按下的方向持续翻页、按住不停**，
  表现出来正是「自己滑到最下方、再往上拖也不动」。
- **这不是窗口化引入的**：优化前整本物化成 DOM 时文档高 1130 万 px（第 4.4.1 节），比现在更长，
  滑块只会更抓不住。

自绘这一条的行为：

- 滑块长度按 `视口高度 / 全书高度` 计算，**下限 24px**，因此永远抓得住；整本装得下一屏时整条隐藏。
- **拖动 = 按全书比例定位**（文档与正文是一比一的，`scrollTop / max` 就是全书进度，与目录面板的进度滑条
  同一套换算）。拖动是粗调：1px 轨道 ≈ 10 屏。
- **点空白轨道 = 翻一屏**（一比一，正好一个视口高度），点滑块上方向上、下方向下。
- **滚轮、PageUp/Down、空格、Home/End 全部保持原生滚动**，手感不变。滚轮落在轨道上也会转发给正文，
  右侧不留死区。
- 用过滚动条之后把焦点交给 `.reader-scroll`：它是 `tabindex="0"` 的滚动容器，失去焦点就没法键盘翻页。
  代价是 Chromium 把程序化聚焦也算作键盘焦点（实测即使刚发生过真实鼠标点击，`focus()` 之后
  `:focus-visible` 依旧成立），默认轮廓会把整块正文框起来；因此指针路径挂 `.is-pointer-focus` 压掉轮廓，
  用户一按键盘就摘掉——键盘焦点仍然保持可见轮廓。
- 位置与长度每次从 `scrollTop/scrollHeight` 现算，不在别处记账：拖动、滚轮、跳章节、窗口重建微调
  `scrollTop` 之后跟着重算一次即可。

**未采用的替代方案：把文档高度压短**，让滑块比例变大。压到滑块有 20px 需要压缩 209 倍，而压缩后
`scrollTop` 的 1px 要分摊 200 多 px 正文：滚轮一格得动不到 0.5px 才等价于现在的滚动感，点一下空白轨道
要跳 200 屏——等于为了滚动条把滚轮和键盘一起废掉。原生滚动条的其它交互（轨道翻页、PgUp/PgDn、
Home/End）都按文档高度换算，与滑块长度要求直接冲突，因此**原生滚动条在这个文档高度上没有可用解**。

### 4.5 阅读进度

- 滚动停止后 500ms 防抖保存，返回书架与关闭窗口前也会保存。
- 关闭窗口时的最后一次保存是**可靠**的：`beforeunload` 用 `sendSync` 把快照同步交给主进程，主进程写入串行化，并在 `will-quit` 里等队列排空后才真正退出（详见第 5.3 节）。
- 保存内容：段落索引、字符偏移、阅读比例、附近文本（前 240 字）、时间戳。
- 恢复顺序：**附近文本匹配 → 段落索引 → 阅读比例**。
  - ⚠️ 第三个分支实际不可达，见第 9 节。
- 恢复位置用 `paragraphWindow.scrollToIndex(i)`（窗口化后不再用 `scrollIntoView`——屏幕外的段落按定义就不在 DOM 里）。位置由偏移表换算，`scrollTop` 天然是跳变：`.reader-scroll` 不带 `scroll-behavior: smooth`，程序化滚动默认就是跳变。实测同一本书同一次恢复，平滑滚动要 924 ms 才停、且 206 ms 后才出现第一次可见移动，跳变只要 41.5 ms。
- 原文件内容变化时通过文件指纹检测，并提示已尽量恢复位置。

### 4.6 阅读设置

- 字号、行距、段落间距、版心宽度、字体（宋体/黑体风格）、段首缩进开关。
- 调整即时预览并自动保存。设置类改动合并到下一帧统一应用（`requestAnimationFrame`，落地时取当前值，因此快速拖动不会停在中间态），落盘防抖 400ms。**结构类改动（导入、移除、重新定位、打开书籍）仍然立即落盘**，不受防抖影响。
  - 单次应用的开销已由窗口化渲染降到毫秒级（改一次字号 = 重排窗口内 401 段 + 重估全书，实测 134k 段共约 6.5 ms），因此滑条可以跟手。按帧合并解决的是「同一次拖动里的多个 `input` 各触发一次」这件另一件事。
- **窗口尺寸变化后重排**：`resize` 监听（按帧合并）重新取当前书的设置并走一次 `setLayout`，因为版心宽度取自 `content.clientWidth`，与窗口宽度相关。
- 支持「恢复默认设置」。
- **按书记忆**：每本小说可保存独立设置，未单独设置时继承全局默认。

### 4.10 章节目录与章节跳转

工具栏左端的「目录」按钮打开目录侧栏（**从界面左侧滑入**，与阅读设置面板的右侧滑出相对），列出识别出的章节，点击即跳转到该章开头。章节条目字号 15px。

目录按钮为圆角矩形文字按钮（`.toolbar-label-button`，「目录」两字在 `.icon-button` 的 36px 圆形里装不下），返回键与 `Aa` 仍是圆形按钮。面板打开时该按钮被面板遮住，关闭靠面板的 × 或点击遮罩。

**当前章节高亮**取「视口顶部所在段落的**真实**索引」与章节表比对：`paragraphWindow.topIndex()` 在**偏移表**上做二分查找（约 12 次数组比较，**不读任何元素几何**）；滚动期间的重算由 `scheduleActiveChapterRefresh()` 收敛进 `requestAnimationFrame`，每帧最多算一次。

⚠️ **不能用「滚动比例 × 段落数」估算当前段落**。那个估算假定段落等高，而真实小说的段落长短悬殊（对话密集段与长描写段可以差好几倍），误差沿全书累积。实测一本段落长度递增的合成书跳到第 5 章时，估算落在第 3 章——表现为跳转本身没错、但目录高亮的是另一章。滚动期间只在章节变化时改 DOM。

识别在**打开书籍时**对内存中的段落执行（`src/reader.js` 的 `detectChapters`）：

- 只认**整段即标题**的段落，段首锚定且尾部限长 24 字，正文里提到「第一章」的长句不会命中。
- 支持阿拉伯数字、全角数字与中文数字（`十一` = 11、`一百零五` = 105），量词支持 章节回卷部篇集，可带 `【】（）《》` 等包裹符号，也认 序章/序言/楔子/引子/前言/后记/尾声/终章/番外/附录 等特殊标题。
- 命中段落少于 2 个，或数字序列不满足大体递增（阈值 0.6）时，**整本放弃识别**——宁可漏判，也不把正文句子塞进目录。

**识别失败时不显示空目录**：面板改为说明未识别到章节标题，并降级为按百分比跳转的滑块（同时显示滚动时同步更新的百分比）。识别成功时，面板顶部显示章节总数。

目录**不写入 `library.json`**。核心约束 1 于 2026-09-28 放宽后（允许保存「有限的正文片段」），章节标题已不再是禁止落盘的内容，**这里仍然选择不落盘**——理由是收益不足以抵消代价：识别一本 133,632 段（基准口径 8.47 MB）小说的全部章节实测 9.6 ms，只占打开耗时的极小一部分（窗口化之后打开一本的瓶颈已经是文本流水线——解码 237.5 ms、规范化 36.8 ms、分段 37.3 ms，见 `docs/changes/2026-09-28-阅读性能优化.md`），为省这点时间把上千条正文派生字符串写进 `library.json` 并不划算。因此每次打开书籍重新计算，不缓存。

### 5.3 IPC 接口（真实）

| 通道 | 方向 | 作用 |
|---|---|---|
| `library:load` | invoke | 读取书架数据 |
| `library:save` | invoke | 保存书架数据 |
| `library:save-on-exit` | **sendSync** | 窗口关闭前同步落盘。用 sendSync 是为了让渲染进程 `beforeunload` 里的这次提交确定性地先于窗口关闭到达；主进程立刻回值，不等磁盘 |
| `library:remove` | invoke | 移除某条书架记录 |
| `book:choose` | invoke | 打开文件选择器并读取 |
| `book:read` | invoke | 按路径读取小说 |
| `book:inspect` | invoke | 检查文件是否可用/变化 |

**写入串行化与退出兜底**（`electron/main.js`）：`store.save()` 是「写 `.tmp` → 备份 `.bak` → `rename`」三步，两次并发会把 `.tmp` 互相覆盖、导致三个文件互不一致。因此所有写入都过 `queueSave()`，串成一条链，`library:remove` 的内部写入也走同一条链。

退出路径用 `will-quit` 而不是 `before-quit`：`will-quit` 在所有窗口关闭之后触发，此刻渲染进程的 `beforeunload` 一定已经交出了最后一份快照；`before-quit` 早于窗口关闭，在那里等待等于等一份还不存在的写入。处理器先 `event.preventDefault()`，等 `saveChain` 排空后再调 `app.quit()`。

> 这条路径**原先是坏的**：旧实现是 `void store.save(data)`，起个头就放行退出，进程可能死在 `writeFile(.tmp)` 与 `rename` 之间。2026-09-28 在用户数据目录里实测到 `library.json.tmp` 残留，且 `.bak` 的 mtime 停在上一次保存——证明 `copyFile` 根本没执行到。已修复，复现方式见 `docs/changes/2026-09-28-阅读性能优化.md` 验收标准第 10 条。

### 5.4 打包与分发（真实）

配置写在 `package.json` 的 `build` 字段。**不新建独立配置文件**——项目是 `"type": "module"`，独立配置需要处理 ESM 导出，写进 `package.json` 没有这个问题，也少一个文件。

| 项 | 值 |
|---|---|
| `productName` | `书页之间`（exe 名、窗口与任务栏显示名） |
| 目标 | `zip`，Windows x64 免安装目录版 |
| 产物 | `release/novel-reader-<version>-win-x64.zip`（约 105MB）；中间产物 `release/win-unpacked/` |
| `files` | `dist/**`、`electron/**`、`design/app-icon/final/icon.ico`、`package.json` |
| `asar` | `true` |
| `win.icon` | `design/app-icon/final/icon.ico`（构建时嵌入 exe 资源段） |
| 命令 | `npm run dist`（= `npm run build && electron-builder --win`） |

**为什么是 `zip` 而不是安装程序或单文件 exe**：解压双击即用、零依赖；不写注册表、不装进 `Program Files`，卸载等于删文件夹。`portable` 单文件每次启动都要把约 200MB 解压到 `%TEMP%`，启动明显更慢；NSIS 安装程序对一个自用工具过重。取舍过程见 `docs/changes/2026-09-27-打包与发布Release.md`。

产物只作为 GitHub Release 附件上传，**不进 Git**（`.gitignore` 的 `/release/` 已覆盖，含 electron-builder 生成的 `builder-debug.yml`）。

**压缩包文件名用 ASCII，包内 exe 仍是中文名**：含中文的压缩包名在部分解压工具与下载链路上有编码风险，ASCII 避开该问题，同时不影响用户实际使用的 exe 名称。

⚠️ **`files` 是白名单，`node_modules` 不在其中。** 当前主进程只用 Node 内置模块（`node:path`、`node:fs` 等），编码解码用内置 `TextDecoder`，**不需要任何运行时依赖**，所以安全。若将来引入运行时依赖（非 devDependency），必须把 `node_modules/**` 加回 `files`，否则打包后启动即报模块找不到。

⚠️ **`electron` 必须在 `devDependencies`。** electron-builder 直接拒绝 `electron` 出现在 `dependencies` 中（报 `Package "electron" is only allowed in "devDependencies"`）——打包产物自带 Electron 运行时，不依赖 npm 装的那个包。本项目原先把它放在 `dependencies`，打包时才发现。

⚠️ **数据目录与产品显示名刻意解耦。** `electron/main.js` 在 `app ready` 之前显式执行 `app.setPath('userData', <appData>/local-novel-reader)`。原因：`app.getPath('userData')` 默认跟随 `app.getName()`，而 `app.getName()` 跟随 `build.productName`。若不显式固定，引入 `productName` 会让数据目录从 `%APPDATA%\local-novel-reader\` 变成 `%APPDATA%\书页之间\`，**老用户的书架会凭空变空**（文件没丢，但应用看不到）。显式 `setPath` 让开发态与打包态共用同一个目录，零迁移。

⚠️ **图标要同时配两处，漏一处不会报错。** `build.win.icon` 是**构建期**读取，负责把图标嵌进 exe 的资源段（资源管理器、任务栏、开始菜单看到的）；`BrowserWindow.icon` 是**运行时**读取，负责窗口自身（主要是开发态可见）。后者要求文件真的在 asar 里，所以 `files` 白名单必须收录它——**不加白名单的表现是开发态图标正常、打包后退回默认图标，且构建过程一声不吭**。运行时路径写成 `path.join(__dirname, '..', 'design', 'app-icon', 'final', 'icon.ico')`：开发态 `__dirname` 是仓库的 `electron/`，打包态是 `app.asar/electron/`，该相对位置两边都成立，**同一个表达式通用，图标只保留一份**。

⚠️ **没有走 electron-builder 默认的 `build/icon.ico`。** 本仓库 `.gitignore` 有根锚定的 `/build/` 规则，把图标放进那里会被静默排除在 Git 之外。改用显式路径 `design/app-icon/final/icon.ico` 避开，`.gitignore` 无需改动。图标的设计说明、三个备选方案与生成脚本见 `design/app-icon/README.md`。

**未做**：安装程序、跨平台打包、自动更新。均属独立需求，不在本次范围内。

```jsonc
{
  "version": 1,
  "settings": {              // 全局默认设置（新导入小说继承）
    "fontSize": 18,
    "lineHeight": 1.9,
    "paragraphSpacing": 0.9,
    "contentWidth": 720,

    "indent": true
  },
  "books": [
    {
      "id": "<文件绝对路径>",
      "path": "<文件绝对路径>",
      "name": "<去掉 .txt 的显示名>",
      "fileName": "<原始文件名>",
      "size": 123456,
      "modifiedAt": "<ISO 时间>",
      "fingerprint": "<sha256 前 24 位>",
      "encoding": "utf-8",
      "importedAt": "<ISO 时间>",
      "lastOpenedAt": "<ISO 时间>",
      "unavailable": false,
      "progress": {
        "paragraphIndex": 0,
        "charOffset": 0,
        "ratio": 0,
        "context": "<附近文本前 240 字>",
        "updatedAt": "<ISO 时间>"
      },
      "settings": null         // null = 继承全局；否则为完整设置对象
    }
  ]
}
```

**关键不变量**：`books[i].id` 等于文件绝对路径。重新定位文件时会同时更新 `id` 与 `path`。

> **`progress.paragraphIndex` 的取值来源在 2026-09-28 变了，字段本身没变**：窗口化渲染之前它是
> 「滚动比例 × 段落数」的估算值（段落长度不均时可能偏离十几章），现在是视口顶部那一段的**真实序号**（偏移表二分查找）。
> 类型、含义、读写方式都没动，**旧记录照常读取，不需要迁移**。见第 9 节第 7 条。

### 性能基准 `npm run bench`（`electron tools/bench-reader.mjs`）

不是断言式测试，是**可重跑的测量脚本**，用来验证优化是否真的生效、也用来回归。默认取书架上已有书籍的路径（只读路径，正文只留在内存），也可 `npm run bench -- <TXT 路径>`。全程把 userData 指向临时目录，**不写入任何用户数据**，仓库里也不含本机个人路径。

测量分两段：文本流水线（解码/规范化/分段/章节识别/拼 HTML，主进程）与排版（渲染进程）。渲染段用真实 `src/styles.css`、按真实段落数与平均段长合成段落——把整本正文通过 IPC 送进渲染进程本身就要花可观时间，会污染待测的数。

排版段刻意把**两种 DOM 形态都测一遍**：「整本一次性物化」是窗口化之前的形态，留作对照基线；「窗口 + 上下垫片」是现在实际用的形态。两组数字放在一起才看得出窗口化省掉了多少。

**已知的测量边界**（引用这些数字时必须一起说明）：不含 Electron IPC、真实正文的 HTML 生成、与段落无关的样式重算；滚动数字不含窗口重建那一下（约每滚过 150 段一次、每次 4～5 ms）；打开与导入没有端到端计时。因此验收标准 1、2 的「单次 `input` 同步耗时 < 30 ms」只能由用户在真实应用里测量判定。

`tools/` 不在 `package.json` 的 `build.files` 白名单里，因此不会进入打包产物。

| `windowing` | **窗口化渲染**。用 4000 段的 `large` 夹具（整本 4200 段）：首屏 DOM 只有 201 段（断言 < 700）、底部垫片 334,690px、跳到第 150 章精确落到该章标题且 DOM 仍 < 700 段、改字号后视口顶部仍是第 3150 段（**落点不漂移**，这是窗口化最容易被改坏的不变量） |
| `scrollbar` | **自绘滚动条**。用同一份 `large` 夹具：原生滚动条不再占宽度（`offsetWidth - clientWidth === 0`）、滑块长度 ≥ 24px、滚轮落在轨道上照常滚正文、点轨道下方正好翻一屏（764px）、拖到轨道中间落到 4200 段的第 2096 段（50.0%）且滑块画在轨道 50% 处、**再拖 10% 只前进 10%**（这是原来「一拖就到底」的直接回归断言） |
| `scrollbar-short-book` | 用 5 段的 `tiny` 夹具：整本装得下一屏时整条滚动条隐藏、滑块不占位 |

> `windowing` 用 4000 段夹具而不是既有的 200 段夹具，是因为 **200 段整本装得进 401 段的窗口**，
> DOM 段数断言在窗口化前后都会通过——那样的断言测了等于没测。

## 10. 需求分级说明（重要）

阅读 v1.0.0 方案时必须区分三类内容，**不要把推荐方案当成不可修改的硬性要求**：

### 10.1 已确定的项目要求（不可随意更改）

第 3 节列出的 8 条核心约束，以及：核心用户流程（导入、再次打开、阅读与自动保存、重新定位、删除记录）、需要保存的字段范围、异常必须给出可执行下一步、四种阅读主题及其「夜间非纯黑」要求。

### 10.2 推荐性技术方案（允许重新评估后调整）

- **Electron 作为桌面运行环境**：方案原文为「推荐第一版使用 Electron」。当前实现采用 Electron，但这是可评估调整的选型，不是硬约束。约束的本质是「必须能稳定保存并复用本地文件路径」，凡满足该约束的方案均可讨论。

## 11. 环境注意事项

1. **本机 `github.com:443` 被阻断**，`api.github.com` 可直连。因此 `gh` 命令正常，但 `git push` 需要走本机代理。当前已在 `.git/config`（仅本仓库）设置 `http.proxy = http://127.0.0.1:7890`。代理未开启时推送会失败。
2. **Electron 二进制安装在 Node 24 下可能失败**：其自带的 `extract-zip`/`yauzl` 会静默中断，导致 `dist/` 里只剩部分文件、`electron.exe` 缺失。可用 PowerShell 对已下载且校验通过的压缩包重新解压修复。
3. 全局 Git 身份未配置（`user.name`/`user.email` 均为空）。本仓库已设置仓库级身份，**未修改全局配置**。
4. 运行方式：`npm run dev` 开发启动；`npm run build` 前端构建；`npm test` 单元测试；`npm run test:ui` 界面回归测试；`npm run dist` 打包 Windows 应用。**不要用浏览器打开 `127.0.0.1:5173`**，那是 Vite 资源服务，不是应用入口。
5. **打包必须走镜像**：electron-builder 默认从 github.com 拉取 Electron 运行时与工具链，本机该域名被阻断。仓库级 `.npmrc` 已设 `electron_mirror` 与 `electron_builder_binaries_mirror` 指向 npmmirror，`build.electronDownload.mirror` 作为第二道保险。**首次打包需下载约 200MB**，缓存在 `%LOCALAPPDATA%\electron-builder\Cache`，第二次起显著加快。
6. **npm 会告警 `.npmrc` 里的镜像键**（`Unknown project config "electron_mirror"`）。**这不是错误**：这两个键是 `@electron/get` 的约定，由 npm 透传成 `npm_config_*` 环境变量供其读取，镜像实际生效（已实测打包成功）。npm 提示未来大版本可能不再透传，届时改用环境变量。
7. **`gh release create` 不需要代理**：它走 `api.github.com` 与 `uploads.github.com`，两者均已实测可达。这与 `git push` 必须走本机代理的情况不同。
