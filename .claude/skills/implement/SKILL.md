# /implement — 执行变更方案

实现 `docs/changes/` 中最新的、尚未完成的变更方案。

## 执行流程

### 1. 读取项目上下文

1. `CLAUDE.md` — 项目级规则与核心约束
2. `docs/PROJECT.md` — 当前真实状态

### 2. 找到待实施的方案

```bash
ls -t docs/changes/
```

选取**最新且状态不是"已完成"**的方案文件。如果存在多个未完成方案，向用户确认要实施哪一个，不要擅自挑选。

### 3. 完整阅读该方案

重点关注：影响范围、数据结构变化、兼容性问题、验收标准、实施步骤。

### 4. 检查当前代码状态

阅读方案中列出的**需要修改的文件**与**需要新增的文件**，确认：

- 文件是否存在、内容是否与方案描述一致
- 关键函数与数据结构是否仍是方案假设的样子

### 5. 处理冲突

如果当前代码与方案存在**明显冲突**（例如方案假设的函数已被改名、数据结构已变化、前置需求未完成）：

1. **先分析**冲突原因与影响
2. **不要强行修改**
3. 向用户说明冲突点，给出可选处理方式，等待决策

方案本身是几天前写的，代码可能已经变化——冲突时**以实际代码为准**，并说明方案中哪部分已过时。

### 6. 实现

按方案的**实施步骤**进行：

- **不实现方案中没有要求的功能**
- **优先复用现有代码**，新增前先确认是否已有可用实现
- **避免无必要的大规模重构**
- 遵守 `CLAUDE.md` 的核心项目约束与开发原则
- 修改数据结构时，确保旧数据仍可读取

### 7. 测试

```bash
npm test
```

**必须运行相关测试。** 如果方案涉及界面、布局或数据流等单元测试覆盖不到的部分，说明验证方式（例如实际启动 `npm run dev` 手动确认），并如实报告哪些部分未经自动化验证。

### 8. 修复本次引入的问题

修复由本次修改导致的问题。**不要顺手修复无关问题**——如发现无关问题，记录并在总结中提出，由用户决定是否另开变更。

### 9. 核对实现结果

逐条对照方案的**验收标准**，确认是否达成。未达成的必须明确指出，不要含糊带过。

### 10. 更新项目文档

1. **`docs/PROJECT.md`** — 使其反映**当前真实状态**（这是必做项）
2. **`docs/ROADMAP.md`** — 仅当未来规划确实发生变化时更新
3. **`docs/CHANGELOG.md`** — 在顶部插入本次完成的变更条目（**不要删除历史条目**）
4. 将对应的变更方案文件状态标记为 **"已完成"**，并补充实施记录与日期。**不要删除该文件。**

## 完成后必须总结

按以下清单逐项汇报：

- **修改了什么**
- **新增了什么**
- **删除了什么**
- **修改了哪些文件**（列出路径）
- **测试结果**（实际执行的命令与结果；未验证的部分要说明）
- **是否有遗留问题**
- **`docs/PROJECT.md` 是否更新**
- **`docs/ROADMAP.md` 是否更新**
- **`docs/CHANGELOG.md` 是否更新**
- **是否适合创建 Git commit**（给出建议的 commit message 前缀与描述）

## 禁止

- **不要自动 push 到 GitHub**（同步由 `/github` 负责）
- 不要自动创建 Git tag 或 GitHub Release
- 不要实现方案范围外的功能
- 不要删除历史需求记录
