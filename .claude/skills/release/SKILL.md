# /release — 版本发布检查

在发布前检查项目状态、文档一致性与测试结果，生成版本发布摘要。

**本 Skill 默认只做检查与整理，不执行任何远程或破坏性操作。**

## 执行流程

### 1. 检查 Git 工作区状态

```bash
git status
git branch --show-current
git log --oneline -10
```

明确：

- 当前分支
- 是否存在未提交修改
- 是否有未纳入版本控制的新文件
- 最近提交记录

### 2. 检查是否存在未完成的变更方案

```bash
ls -t docs/changes/
```

逐份检查状态。如果存在**未完成**的方案：

- 明确指出它们不会被包含在本版本中
- 询问用户是继续发布，还是先完成它们

### 3. 检查测试结果

```bash
npm test
npm run build
```

**实际运行**，不要在未运行的情况下声称通过。如果测试失败或构建失败，**停止发布流程**，先报告问题。

### 4. 总结本版本完成的功能

以**上一个版本**为起点，从 `docs/CHANGELOG.md` 与 Git 历史中整理：

```bash
git log --oneline <上一个版本的提交>..HEAD
```

概括本版本完成的功能、修复、以及已知问题。

### 5. 检查三份文档是否一致

| 文档 | 检查内容 |
|---|---|
| `docs/PROJECT.md` | 描述的状态是否与**当前代码**一致？功能清单有无遗漏或虚报？ |
| `docs/ROADMAP.md` | 已完成的方向是否应移出？未做的方向是否仍准确？ |
| `docs/CHANGELOG.md` | 本版本的条目是否完整记录了实际变更？ |

**发现不一致时不要擅自改动**，先列出差异并说明判断依据，交由用户确认。若确认是文档过时，再更新。

### 6. 建议版本号

依据实际变更情况给出建议，并说明理由：

| 变更性质 | 建议 |
|---|---|
| 仅修复问题、无新功能、无破坏性改动 | 修订号 +1（如 1.0.0 → 1.0.1） |
| 新增向后兼容的功能 | 次版本号 +1（如 1.0.0 → 1.1.0） |
| 数据结构不兼容、架构重大调整、核心约束变化 | 主版本号 +1（如 1.0.0 → 2.0.0） |

**特别提醒**：如果变更影响 `library.json` 的结构且**不能读取旧数据**，属于破坏性变更，应建议主版本号递增。

### 7. 生成版本发布摘要

输出内容：

- 建议版本号与理由
- 本版本新增 / 修改 / 修复 / 移除
- 已知问题
- 与上一版本的兼容性说明（尤其是用户已有书架数据）
- 未包含在本版本中的未完成方案

### 8. 准备版本相关文档（如需要）

仅在用户确认后：

- 在 `docs/CHANGELOG.md` **顶部**插入本版本条目
- 若属于重大版本或重大架构变化，在 `docs/archive/` 保存完整版本快照

## 默认禁止

- **不自动 `git push`**
- **不自动创建 GitHub Release**
- **不自动创建 Git tag**
- **不删除文件**
- **不修改与版本发布无关的代码**

需要打 tag、推送或创建 Release 时，**先征求用户明确同意**。远程同步由 `/github` 负责。
