# /change — 需求分析与变更方案

对用户提出的需求做完整分析，产出一份可执行的变更方案文档。

## 核心规则

**本 Skill 只做分析和方案设计。**

- **不要修改源代码。**
- **不要修改 `docs/PROJECT.md`**（它是"当前状态"，执行阶段才更新）。
- **不要删除历史需求。**
- 生成方案后**停止**，等待用户确认。不要自行进入实现。

---

## 执行流程

### 1. 读取项目上下文

按顺序阅读：

1. `CLAUDE.md` — 项目级规则与核心约束
2. `docs/PROJECT.md` — 当前真实状态、架构、数据结构
3. `docs/ROADMAP.md` — 未来计划，判断本需求是否已在规划中
4. `docs/CHANGELOG.md` — 已完成的变更，避免重复设计

如果 `docs/PROJECT.md` 与实际代码不一致，以**实际代码**为准，并在方案中记录该差异。

### 2. 检查 `docs/changes/` 中已有的未完成需求

```bash
ls docs/changes/
```

阅读其中的文件，确认：

- 是否已有与本需求相关的方案
- 是否存在尚未完成、且会被本需求影响的需求
- 是否存在相互冲突的需求

如果新需求与已有未完成方案冲突，**先指出冲突并询问用户**，不要擅自合并或覆盖。

### 3. 检查相关代码

根据需求定位相关模块，阅读真实实现（不要凭文件名猜测）。常用入口：

| 需求类型 | 优先查看 |
|---|---|
| 导入 / 编码 / 文件 | `electron/book-service.js`、`electron/main.js` |
| 存储 / 数据结构 | `electron/library-store.js`、`src/store.js` |
| 阅读器 / 排版 / 进度 | `src/reader.js`、`src/styles.css` |
| 界面 / 交互 | `src/main.js` |
| 通信接口 | `electron/preload.mjs` |

### 4. 判断需求类型

明确归类（可多选）：新功能 / 功能修改 / Bug 修复 / 重构 / UI 调整 / 性能优化 / 其他。

### 5. 影响分析

**必须逐条明确说明**：

- 当前系统哪些地方受到影响
- 哪些代码可以复用
- 哪些模块需要修改
- 哪些模块需要新增
- **是否需要修改数据结构**
- 是否影响已有功能
- **是否影响已有用户数据**（`library.json` 兼容性）
- 是否需要修改项目架构
- 是否需要更新 `docs/PROJECT.md`
- 是否需要更新 `docs/ROADMAP.md`

### 6. 创建变更方案文档

路径：`docs/changes/YYYY-MM-DD-简短名称.md`

使用当天日期与简短中文名称（如 `2026-09-28-章节目录.md`）。**文件名不要覆盖已有文件**，重名时追加序号。

文档至少包含以下小节：

```markdown
# <需求标题>

- 状态：待实施
- 类型：<新功能 / 功能修改 / Bug 修复 / 重构 / UI 调整 / 性能优化>
- 创建日期：YYYY-MM-DD
- 关联需求：<相关 changes 文件，无则写"无">

## 需求描述
用户提出的原始需求，以及澄清后的准确表述。

## 需求背景
为什么需要它，解决什么问题。

## 当前项目状态
与本次需求相关的现有实现（引用真实文件与行为）。

## 变更原因
为什么必须改动，不改会怎样。

## 影响范围
受影响的模块、功能、数据结构、用户数据。

## 技术实现方案
具体怎么做。说明关键取舍与被否决的替代方案。

## 需要修改的模块

## 需要新增的文件

## 需要修改的文件

## 数据结构变化
`library.json` 是否变化；旧数据如何读取；是否需要迁移。

## 兼容性问题
对已有书架记录、阅读进度、阅读设置的影响。

## 潜在风险
可能引入的问题，以及对应的验证或回退方式。

## 验收标准
可验证的具体条件，避免"体验更好"这类无法判定的表述。

## 实施步骤
有序、可执行的步骤清单。
```

### 7. 校验方案与项目约束

提交方案前自查：

- 是否触碰 `CLAUDE.md` 中的**核心项目约束**？（如复制小说正文、上传数据、擅自增加服务器/账号）
- 是否**擅自扩大项目范围**？
- 是否与 `docs/ROADMAP.md` 的"明确不做的方向"冲突？
- 是否把 v1.0.0 方案里的**推荐性技术方案**当成了硬性要求？
- 验收标准是否可验证？

若触碰核心约束，必须在方案中**显著标明并说明理由**，交由用户决策。

---

## 完成后

停止操作，并告知用户（原样输出第一句）：

> 变更方案已生成，确认后可以执行 /implement。

同时简要说明：方案文件路径、需求类型、影响范围要点、以及任何需要用户先决策的问题。

**不要**在此时开始实现，也不要修改 `docs/PROJECT.md`。
